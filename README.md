# Manta — Platform Monorepo

Реализация интеллектуальной платформы анализа матчей Dota 2 по
[спецификации v2.0.0](docs/specification/ru/README.md).

### Что уже работает (проверено против живой инфраструктуры)

Полный конвейер: **OpenDota/загрузка → MinIO → Kafka → C++ парсер →
ClickHouse → фичи → модели (Win Probability, Death-Risk) → отчёты с
разбором ошибок → веб-UI** — на реальных матчах, включая про-эталон.

- `deployments/docker-compose.yml` — PostgreSQL 16, ClickHouse 24.8, Kafka 3.8 (KRaft), Redis 7, MinIO, MLflow (backend в postgres); все с healthcheck.
- `infra/migrations/` — реляционная схема Гл. 4.2, аналитический слой Гл. 4.4 (ReplayEvents, EconomyTimeline, PositionSnapshots) пер-матчевые MatchDraft/MatchEvents и витрины фич (PlayerMatchFeatures, MatchTimelineFeatures).
- `apps/api-gateway` — Go: upload → MinIO + outbox → Kafka; статусы AnalysisJob по `replay.parsed`/`dlq.parser`; REST `/matches`, `/timeline`, `/analysis`, `/heroes`, `/draft/simulate`; RFC 7807, trace_id, rate limit.
- `apps/data-collector` — Python, 6 источников (реплейный OpenDota + гибридный JSON-путь `opendota-timeline`/`-pro` + GraphQL STRATZ `stratz-timeline`/`-pro`): дедуп/курсор в PG, 429-бэкoff до сброса квоты, авто-reconnect к Postgres. **Шардирование между машинами** (`COLLECTOR_SHARD_COUNT`/`COLLECTOR_SHARD_ID`) — см. ниже. Из скачанного JSON извлекаются драфт, события (Рошан/аегис/FB/бэйбеки/руны/варды) и 12 поминутных фич (`collector/signals.py`), сам JSON складывается в MinIO (`collector/rawstore.py`) — чтобы будущие фичи бэкфиллились без квоты.
- `apps/replay-parser` — C++17-ядро (битово-совместимый с `dotabuff/manta` декодер сущностей: позиции, экономика, combat log; 110 МиБ за ~4 с) + Go-сервис `svc/` (Kafka → ядро → ClickHouse → `replay.parsed`, DLQ).
- `apps/feature-extractor` — Python: `replay.parsed` → point-in-time фичи (GPM/XPM, LH/DN, alive/towers/rax diff, networth_rel) → витрины + `features.calculated`; пушит срез в Feature Store.
- `apps/ml-service` — gRPC :50051 (Predict/PredictStream); Win Probability (LightGBM + OOF-изотоника, 42 фичи, Brier ≈ 0.14), Death-Risk (P смерти за 30с, AUC 0.79), Laning (P выиграть линию по игре первых 5 минут, AUC 0.89) и Draft Prior (P(win\|составы), AUC 0.585) из общего реестра моделей (S3/MLflow).
- `apps/report-generator` — WP-кривая, SHAP-атрибуция ошибок, модельный Safety Index, позиции смертей → MatchReports.
- `apps/similarity`, `apps/draft`, `apps/coach`, `apps/feature-store` — gRPC-сервисы (:50052–:50055) поверх витрин/эмбеддингов.
- `apps/frontend` (React+TS+Vite) — список матчей, страница матча (WP-бейдж, SHAP-чипы, карта смертей, риск-бейджи), драфт-симулятор.

## Быстрый старт

```bash
make up        # поднять инфраструктуру
make migrate   # применить миграции PG + CH
make topics    # создать Kafka-топики

# запустить шлюз
cd apps/api-gateway && go run ./cmd/server

# проверить
curl localhost:8080/healthz
curl -X POST localhost:8080/api/v1/matches/upload -F "file=@replay.dem"
```

Весь стек — от инфраструктуры до веб-интерфейса — поднимается одной
командой (идемпотентно: живые компоненты не трогает, безопасно запускать
повторно и после любого перезапуска среды/ПК):

```bash
MANTA_TRAIN_ENV=~/manta-train.env make recover
```

`scripts/dev-recover.sh` запускает: dockerd → инфраструктуру (PG, CH,
Kafka, MinIO, Redis) → топики и миграции (идемпотентно, журнал
`SchemaMigrations`) → парсер, экстрактор, коллекторы, ml-service,
similarity/draft/coach/feature-store, report-generator, auto-train →
**api-gateway (:8080), веб-интерфейс (:5173) и дашборд (:9107)** — и
заканчивается health-check'ом `make doctor`. Env-файл с секретами — вне
репозитория; логи сервисов — `~/manta-logs` (`MANTA_LOG_DIR`), не `/tmp`.

### Одна команда: `manta up`

`scripts/manta` — единая точка входа. Ставится на PATH один раз:

```bash
sudo ln -s "$HOME/manta/scripts/manta" /usr/local/bin/manta
```

Дальше весь жизненный цикл — четырьмя словами:

```bash
manta up        # git pull → поднять весь стек → восстановить бэкап, ЕСЛИ
                #   датасет пуст → дашборд (:9107); всё одной командой
manta down      # остановить хостовые процессы (контейнеры и данные целы)
manta doctor    # health-check по данным
manta backup    # слепок датасета (+ оффсайт в облако, если настроен)
```

`manta up` = `git pull --ff-only` (не проходит при расхождении — тогда
продолжает на текущем коде) → `make recover` → **условное восстановление**.
Восстановление срабатывает, только когда витрина практически пуста
(< `MANTA_RESTORE_THRESHOLD`, по умолчанию 100 матчей): свежая машина
после переустановки подтянет последний бэкап (локальный каталог в
приоритете, иначе из облака через rclone) и вернётся с данными. На машине
с данными этот шаг пропускается — локальные данные новее бэкапа, и
подмешивать старое не нужно.

`manta restore` — принудительно влить последний бэкап поверх текущих
данных (безопасно: ReplacingMergeTree оставляет более свежую версию
строки, добавляются лишь недостающие матчи).

Обмен между машинами требует явного списка доверенных меток:
`MANTA_PEER_HOSTS=home-pc-1,home-pc-2`. Спринт 158 добавил в каждый
слепок `MANIFEST.sha256`: импорт проверяет полный состав и SHA-256 до
распаковки и не принимает старые архивы без manifest.

После recover открывать: веб-интерфейс http://localhost:5173, живой
дашборд http://localhost:9107.

### Панель обучения (:9107)

> Как устроена модель, что означает каждая метрика и как отличить
> работающую модель от сломанной — **`docs/MODEL-GUIDE.md`**.

Раздел «Обучение модели» показывает то, ради чего дашборд открывают во
время сбора:

- **фазовые Brier** (early / mid / late) плюс valid и про-эталон —
  агрегат маскирует, что поздняя игра тривиальна, а ранняя как раз там,
  где модель слаба. Про-матчи с 2026-07-31 делятся между обучением и
  эталоном (`PRO_TRAIN_FRAC`, по умолчанию 0.5): раньше весь про-tier был
  holdout'ом, модель не видела этот домен вовсе — и получала на нём
  skill 0.27 против 0.58 на пабликах. `PRO_TRAIN_FRAC=0` возвращает
  прежнее поведение;
- **рост датасета по дням** за 30 дней — пустой столбец сразу виден, это
  день, когда сбор стоял;
- **дрейф фич (PSI)**, худшие сверху: большие значения означают, что
  модель обучена не на том, что приходит сейчас;
- **таблица ablation** — какая группа фич заслужила место (Δ = Brier без
  фичи минус Brier со всеми, Δ>0 → фича полезна). Заполняется кнопкой
  «Ablation фич».

Данные берутся из уже опрашиваемых источников: Prometheus auto-train,
ClickHouse и JSON-отчёта ablation. Читать артефакт модели напрямую было
бы свежее, но потянуло бы lightgbm в дашборд, который намеренно живёт на
голой стандартной библиотеке и обязан подниматься, когда всё лежит.

### Панель управления (:9107)

Дашборд не только показывает телеметрию, но и запускает конвейер:
кнопки «Поднять всё», «Проверить», «Статус обучения», «Переобучить WP»,
«Ablation фич», «Остановить сервисы» — с живым логом прямо на странице.

Страница, умеющая выполнять команды, — это удалённое выполнение кода,
поэтому защита из трёх слоёв:

- слушает **127.0.0.1** (`DASHBOARD_BIND`); если бинд не петлевой,
  действия отключаются, пока не задан `DASHBOARD_ALLOW_REMOTE_ACTIONS=1`;
- POST требует заголовок `X-Manta-Action: 1` — без него чужая открытая
  в браузере страница могла бы отправить форму на localhost и остановить
  сбор (браузер не пошлёт нестандартный заголовок кросс-доменно);
- действия — фиксированный список, аргументы зашиты в коде; поля
  «введите команду» нет.

Из Windows панель доступна как обычно по `localhost` — проброс WSL2
работает и для 127.0.0.1.

**`make stop` дашборд НЕ останавливает** — иначе кнопка «Поднять всё»
исчезла бы вместе с сервисами. Остановить его отдельно:
`pkill -f scripts/dashboard.py`. Первый запуск на свежей машине —
по-прежнему `make recover` из терминала или задача автозапуска.

**Обновление кода**: recover не перезапускает уже живые процессы (`if !
pgrep`), поэтому после `git pull` они останутся на старом коде — всё
«up», а нового поведения нет. Штатный порядок (подробности —
`docs/runbooks.md` §5):

```bash
make stop        # только хостовые процессы; контейнеры и данные не трогаются
git pull origin main
make migrate
MANTA_TRAIN_ENV=~/manta-train.env make recover
make doctor
```

Проверить здоровье конвейера в любой момент — по ДАННЫМ, а не по процессам
(топики, лаг консьюмер-групп, свежесть таблиц, квота OpenDota, часы,
миграции):

```bash
make doctor
```

Понять, **почему упал темп сбора** и какие фичи реально заполняются
(doctor на этот вопрос не отвечает: его пороги свежести — часы, а
пятикратное падение притока он считает нормой):

```bash
make collect-report                 # приток по источникам, квоты, логи, фичи
make collect-report ARGS=rate       # только темп сбора
make collect-report ARGS=features   # только покрытие фич
```

Отчёт ничего не меняет и не перезапускает — только читает.

## Безопасность: JWT, TLS, GDPR

По умолчанию на локальном стенде gateway слушает HTTP и пускает без
токенов (в логе — WARN `auth_disabled`/`tls_disabled`). Включить:

```bash
./scripts/gen-dev-keys.sh            # ключи RS256 + самоподписанный TLS
# прописать выведенные пути в ~/manta-train.env, затем make recover
```

На VPS этот fallback запрещён: overlay задаёт `MANTA_PROD=1`, монтирует
JWT public key и TLS pair read-only, а gateway проверяет их до первого
подключения к инфраструктуре. Приватный JWT-ключ остаётся на хосте для
`issue-token.sh`. Frontend и Prometheus обращаются к gateway по HTTPS с
проверкой смонтированного сертификата; наружу порт по-прежнему доступен
только на `127.0.0.1`.

После этого API работает по HTTPS (TLS 1.3, версии ниже отвергаются), а
закрытые эндпоинты требуют Bearer-токен. Роли Гл. 9.3: `anonymous` —
матчи/разборы/герои/драфт, `free` — загрузка реплеев, `premium` —
GDPR-экспорт, `admin` — выпуск токенов и стирание данных.

```bash
./scripts/issue-token.sh admin       # первый токен (локально, ключом)
curl -sk https://localhost:8080/.well-known/jwks.json
curl -sk -X POST https://localhost:8080/api/v1/auth/token \
     -H "Authorization: Bearer $ADMIN" \
     -d '{"sub":"user-1","role":"premium"}'
```

GDPR (Гл. 9.7): `GET /api/v1/players/{ник}/export` — все данные субъекта
одним JSON; `DELETE /api/v1/players/{ник}/data` — стирание никнейма из
витрины и отчётов (игровая статистика остаётся обезличенной). Субъект
идентифицируется никнеймом: account_id платформа не хранит.

**Псевдонимизация никнеймов** (спринт 70, по умолчанию выключена):

```bash
MANTA_PII_MODE=pseudonymize
MANTA_PII_SALT=$(cat ~/manta-keys/pii-salt)   # создаёт gen-dev-keys.sh
```

В этом режиме витрина и отчёты хранят `player_hash =
HMAC-SHA256(соль, casefold(ник))[:16]` вместо самого ника. Обратной
таблицы нет: GDPR-операции работают вперёд (субъект называет ник — шлюз
его хеширует и ищет), а интерфейсу имя не нужно — он показывает героя.
Соль после начала сбора не менять: она связывает ник с уже записанными
псевдонимами. Подробности и открытые пункты — `docs/security-review.md`.

### mTLS между внутренними сервисами

По умолчанию gRPC-сервисы (:50051–:50055) слушают открыто и пишут в лог
WARN `mtls_disabled`. Включить — задать все три переменные (частичная
конфигурация намеренно оставляет режим insecure, а несуществующий путь
роняет сервис, а не откатывает в открытый режим):

```bash
MANTA_MTLS_CA_FILE=~/manta-keys/mtls-ca.pem
MANTA_MTLS_CERT_FILE=~/manta-keys/mtls-cert.pem
MANTA_MTLS_KEY_FILE=~/manta-keys/mtls-key.pem
```

Сервер требует сертификат клиента (`require_client_auth=True`), поэтому
посторонний процесс не подключится к ML Service, даже находясь на той же
машине. Обвязка — `libs/manta_grpc`, тесты поднимают настоящий сервер и
проверяют отказ клиенту без сертификата и с сертификатом чужого CA.

### Retention отчётов и раздельные роли БД

Отчёты содержат PII и растут без ограничения. Чистка выключена по
умолчанию; включается сроком хранения, а CLI по умолчанию только
показывает, что удалилось бы:

```bash
python -m reportgen.retention                     # сухой прогон
python -m reportgen.retention --days 180 --apply  # удалить
# в env-файле: REPORTS_RETENTION_DAYS=180 — report-generator чистит раз в сутки
```

Отчёт — производный артефакт: исходные данные остаются в ClickHouse, и
он пересоздаётся через `python -m reportgen --match ID`.

На VPS сервисы ходят в Postgres под раздельными учётками с минимальными
правами. Миграция 005 создаёт групповые роли, а bootstrap после миграций
автоматически создаёт login-пользователей и только затем запускает
приложения. Коллекторы используют `manta_collector_user`, генератор
отчётов — `manta_reports_user`, gateway — `manta_gateway_user`.

Для ручной установки пользователей:

```bash
MANTA_DB_PASS_COLLECTOR=$(openssl rand -hex 16) \
MANTA_DB_PASS_REPORTS=$(openssl rand -hex 16) \
MANTA_DB_PASS_GATEWAY=$(openssl rand -hex 16) \
MANTA_DB_PASS_RO=$(openssl rand -hex 16) \
  ./scripts/create-db-users.sh
```

Пароли генерируются независимо и хранятся только в `deployments/.env`.
Администратор `dota` остаётся у миграций и host-скриптов; в прикладные
контейнеры VPS его DSN больше не передаётся. Базовый compose сохраняет
прежний dev-режим для домашней машины.

MinIO на VPS также разделён по функции: `manta_ingest` ограничен
бакетами `replays` и `matches-json`, parser читает и удаляет только
реплеи, runtime ML читает `models`, а публиковать модели может только
`manta_model_writer` у `ml-autotrain`. При публикации в metadata
фиксируется SHA-256 артефакта; `resolve()` сверяет digest до `joblib.load`
и отказывается загружать повреждённую или подменённую модель.

Остальные stateful-сервисы VPS также закрыты от lateral movement:
ClickHouse выдаёт отдельные `manta_ch_reader`, `manta_ch_writer` и
`manta_ch_trainer` с минимальными грантами; Redis требует AUTH; MLflow
находится в отдельной internal-сети, к которой подключены только Postgres,
`ml-service` и `ml-autotrain`. Локальный dev-compose сохраняет прежние
необязательные credentials.

## Синхронизация датасета между машинами

Датасет собирается независимо на каждой машине (облако, локалка) и
расходится. Перенос — одной командой в каждую сторону:

```bash
make dataset-export                       # → manta-dataset-<дата>.tar
make dataset-import IN=manta-dataset-….tar  # идемпотентно, повторять можно
```

Переносятся витрины ClickHouse (Replacing-дедуп), сырьё позиций/экономики
(вливаются только новые match_id), дедуп коллекторов и готовые отчёты
(побеждает более свежий `generated_at`). Подробности — в шапке
`scripts/dataset-sync.sh`.

### Параллельный сбор на нескольких машинах (разные IP)

Квота OpenDota считается по IP (~3000 запросов/сутки анонимно). Две
машины с разными IP удваивают сбор — но, читая один список матчей, схватят
одни и те же. Шардирование по `match_id % N` разводит их без координации:

```bash
# в env-файле каждой машины (MANTA_TRAIN_ENV), COUNT одинаков, ID разный:
#   ПК №1:  COLLECTOR_SHARD_COUNT=2   COLLECTOR_SHARD_ID=0   # чётные
#   ПК №2:  COLLECTOR_SHARD_COUNT=2   COLLECTOR_SHARD_ID=1   # нечётные
```

Множества собранных матчей не пересекаются, поэтому слияние баз через
`dataset-import` конфликт-фри.

### STRATZ как второй источник деталей (спринт 79)

Узкое место сбора — не список матчей, а **детали**: `/matches/{id}` у
OpenDota стоит вызов на матч и упирается в ~2000/сутки с IP, тогда как
одна страница листинга отдаёт до 100 кандидатов за вызов. STRATZ снимает
ровно этот потолок: кандидаты по-прежнему берутся дешёвым листингом
OpenDota, а поминутные ряды приходят из GraphQL STRATZ (Default-токен —
20/сек, 250/мин, 2000/час, **10000/сутки**).

Токен берётся на stratz.com (раздел API) и кладётся в env-файл — **не в
git**:

```bash
# ~/manta-train.env
STRATZ_API_TOKEN=...        # без него stratz-коллекторы не поднимаются
STRATZ_LIMIT=40             # матчей за цикл (public), интервал 1800с
STRATZ_PRO_LIMIT=10         # матчей за цикл (pro), интервал 3600с
```

`make recover` поднимает `stratz-timeline` и `stratz-timeline-pro` только
при заданном токене — на машине без STRATZ ничего не меняется.

Что STRATZ даёт и чего не даёт. Ядро витрины (`networth_diff`, `xp_diff`,
`kills_*`, `radiant_win`) — из полей `radiantNetworthLeads` /
`radiantExperienceLeads` / `radiantKills` / `direKills`. Позиционные фичи
и фичи трека F остаются **NaN**: первые существуют только в реплее, вторые
собираются из JSON OpenDota. Строки помечаются `feature_version =
stratz-graphql@1`, поэтому источники всегда различимы в датасете:

```sql
SELECT feature_version, count(DISTINCT match_id)
FROM MatchTimelineFeatures GROUP BY feature_version;
```

Патчи переводятся по **имени** версии ("7.39"): `gameVersionId` у STRATZ —
свой идентификатор, и запись его в колонку `patch` молча испортила бы
даунвейт старых патчей при обучении. Не удалось перевести — пишется 0
(«неизвестен»).

**Дублей между источниками нет**, и это обеспечено двумя механизмами.
Первый — общая `CollectedMatches`: матч, собранный любым источником,
остальные пропускают. Второй нужен потому, что первого мало: JSON-путь
OpenDota и STRATZ читают один и тот же листинг с вершины, а дедуп
срабатывает лишь ПОСЛЕ отметки — между проверкой и отметкой лежит запрос
деталей, и в это окно оба успевают взять один матч. Проигрыш в такой
гонке стоит не лишнего запроса, а фич: витрина — `ReplacingMergeTree` по
`(match_id, game_time)`, побеждает строка, вставленная последней, и
бедная строка STRATZ затёрла бы строку OpenDota вместе с треком F.
Поэтому кандидаты детерминированно делятся между источниками
(`SourceSplit`, по `match_id // 10`) — пересечений нет вовсе. Пока
`STRATZ_API_TOKEN` не задан, деление не действует и поток OpenDota не
меняется.

### Бюджет вызовов OpenDota (спринт 130)

Квота OpenDota — **2000 запросов в сутки на IP**, и купить больше нельзя:
платный тариф требует карты, недоступной владельцу. Это жёсткий потолок
и самый дефицитный ресурс проекта.

До спринта 130 он делился по принципу «кто успел». 2026-08-06 это стоило
шести часов простоя ВСЕГО сбора: конвейер кандидатов тратил ~2300
запросов в сутки, квота ушла в минус (`remaining-day = -246`), и следом
легли все остальные коллекторы — включая те, что кормят про-эталон
промоушен-гейта.

Теперь у каждого источника есть **гарантированная доля**, и он сам
останавливается, не мешая соседям:

| источник | доля | зачем столько |
|---|---:|---|
| candidates | 1100 | глубокие матчи с реплеем — главный продукт |
| opendota-timeline | 250 | тонкие строки, дублируют кандидатов |
| opendota-timeline-pro | 200 | **про-эталон гейта, трогать нельзя** |
| opendota-league | 200 | **про-эталон гейта, трогать нельзя** |
| opendota-public | 50 | тонкие строки |
| opendota (pro-replay) | 50 | глубокие про-матчи |
| stratz-timeline | 50 | только листинг кандидатов |

Сумма 1900 из 2000 — сотня в запасе на разовые вызовы вроде
`constants/patch` и на гонку между процессами. Канон — `SHARES` в
`collector/budget.py`: чтобы одолжить чужое неиспользуемое, процесс
обязан знать доли соседей, а из своей переменной окружения он их не
видит. `OPENDOTA_BUDGET` переопределяет гарантию своего процесса.

#### Доля — гарантия, а не потолок (спринт 135)

Жёсткая доля оказалась хуже болезни, которую лечила. Замер 2026-08-07
08:24 UTC: `stratz-timeline` (53/50) и `opendota-timeline` (253/250)
спали **до полуночи**, выбрав свои крошечные доли, — при том что общая
квота была цела на 85% (`remaining-day: 1696`), а приток из всех
источников, кроме реплейного, стоял с трёх ночи. Спринт 130 чинил «один
источник выедает всё» и создал «источники стоят при свободной квоте».

Правило теперь такое:

* доля **гарантирована**: сосед-обжора её не отберёт;
* сверх доли можно брать из общего пула;
* пул сначала резервирует **невыбранные** гарантии соседей;
* резерв **тает вместе с сутками**: в 00:30 чужая невыбранная доля
  удержана почти целиком (сосед ещё успеет ею воспользоваться), к 20:00 —
  на шестую часть. Молчащий весь день источник не держит квоту мёртвым
  грузом до полуночи.

Чего правило НЕ обещает: гарантия сильна ровно настолько, насколько велик
резерв. К вечеру сосед вправе занять чужую невыбранную долю, и
проснувшийся позже получит меньше номинала. Это осознанный обмен —
держать долю молчащего источника до полуночи значит гарантированно её
потерять. Общий пул при этом стена в любом случае: за ним чужой лимит и
429 на весь оставшийся день.

Отсюда же: при исчерпанном бюджете коллектор спит **час, а не до
полуночи**. Потолок растёт в течение суток по мере таяния резерва, и
уложить источник спать на восемнадцать часов значит вернуть ту же
болезнь.

#### Отказ не стоит вызова

Инкремент идёт ПЕРЕД проверкой (иначе два процесса одного источника оба
прочитали бы «ещё можно»), но отвергнутая попытка **откатывается**:
коллектор в этот момент никуда не ходил. Без отката счётчик рос от
каждого отказа, и источник в цикле повторов раздувал и свою строку, и
общий пул. Это видно в поле того же дня: `ApiBudget` насчитал 1304
вызова за сутки, а сама OpenDota — 304.

Счётчик живёт в Postgres (`ApiBudget`), а не в памяти: коллекторы —
отдельные процессы, общий лимит поодиночке не соблюсти, и перезапуск не
должен обнулять потраченное. Ключ включает **день UTC** — ту же границу,
на которой OpenDota сбрасывает свой счётчик, поэтому таблица обнуляется
сама.

Исчерпанный бюджет бросает исключение, а не возвращает `False`. Это не
стилистика: дважды подряд (спринты 126.1 и 129.1) исчерпанная квота
трактовалась как свойство отдельного матча, и цикл продолжал жечь
запросы — во втором случае по шестьдесят за проход при уже отрицательном
остатке. Возвращаемое значение слишком легко проигнорировать.

Что смотреть: `make collect-report ARGS=rate`, раздел «Бюджет вызовов
OpenDota по источникам».

### Кэш рангов по account_id (спринт 123)

Ранговый фильтр STRATZ отбраковывает ~95% матчей, и каждая отбраковка
стоит одного запроса из суточной квоты. Это плата за **одноразовое**
знание: тот же игрок завтра сыграет ещё десять матчей, и мы заплатим за
него ещё десять раз.

Ранг — свойство игрока, а не матча, и меняется он неделями. Значит его
можно купить один раз: опрошенный Immortal делает бесплатно
распознаваемыми все свои будущие матчи. Квота перестаёт быть расходником
и становится накопителем.

Второе применение важнее первого. Своя разбивка реплеев (см. ниже про
потолки) упирается в канал: 58 МиБ на матч. Скачать весь поток нельзя —
надо отбирать **до** скачивания, а Valve ранга не отдаёт вовсе. Кэш и
есть тот фильтр.

Всё это работает **само**, если заданы ключи: `make recover` поднимает
`ranks-scan` (наполняет очередь кандидатов, интервал 10 минут) и
`ranks-fill` (опрашивает очередь рангов, интервал час — под квоту
1500/час). Команды ниже нужны для разовых прогонов и диагностики.

```bash
make ranks-harvest                         # посев из архива, БЕЗ вызовов API
make ranks-seed   ARGS="--matches 2000"    # аккаунты из потока Valve
make ranks-fill   ARGS="--budget 500"      # опросить очередь (OpenDota)
make ranks-fill   ARGS="--budget 1000 --resolver stratz"
make ranks-scan   ARGS="--matches 2000"    # сколько матчей мы бы отобрали
make ranks-report                          # что накопилось
make ranks-probe                           # что разрешено токену STRATZ
```

Топливо для очереди — поток Valve: `GetMatchHistoryBySequenceNum` отдаёт
100 матчей за вызов, то есть до 1000 `account_id`, и лимитов в нашем
масштабе не имеет. Ключ бесплатный, берётся на
`steamcommunity.com/dev/apikey` (аккаунт не должен быть «limited»):

```bash
# ~/manta-train.env
STEAM_API_KEY=...           # только для seed; сбор без него работает как раньше
RANKS_RESOLVER=stratz       # умолчание: stratz при наличии токена, иначе opendota
RANKS_BATCH_SIZE=5          # игроков в запросе STRATZ (предел сервера)
STRATZ_RUN_BUDGET=1000      # запросов за один прогон fill (квота часа — 1500)
```

Про темп отдельно, потому что цена ошибки здесь высокая. Лимиты STRATZ —
8/с, 150/мин, **1500/час**, 15000/сутки, и связывающий из них ЧАСОВОЙ:
он режет темп до одного запроса в 2.4 секунды. Считать паузу по 8/с (то
есть 18 000 запросов в час) значит выбрать часовую квоту за пять минут,
что и произошло в прогоне 2026-08-06.

Исчерпанная квота часа отличается от всплеска принципиально: всплеск
лечится паузой в секунды, квота — только следующим часом. Поэтому 429
при нулевом остатке в заголовках `x-ratelimit-remaining-hour/day`
**не** повторяется: прогон останавливается, сохраняя всё уже полученное,
и сообщает причину. Остаток очереди никуда не денется.

Замеры живых прогонов (2026-08-06):

* пакетный `players(steamAccountIds:)` у STRATZ **разрешён** нашему
  токену — в отличие от `matches(ids:)`. Но ограничен **пятью** id:
  «You have surpassed the maximum take value of : 5». Множитель квоты
  всё равно пятикратный (15 000 запросов → 75 000 игроков в сутки), и
  предел вычитывается из текста ошибки, а не захардкожен;
* Valve отдаёт **429 после ~12 вызовов** `GetMatchHistoryBySequenceNum`
  подряд, даже с паузой в секунду: лимит burst-овый, и пауза его не
  обходит — обходит отступление (2/4/8/16 с);
* OpenDota ответил на **76 из 200** запрошенных аккаунтов: свои ~2000 в
  сутки он делит с коллекторами. Поэтому `fill` теперь печатает причины
  молчания, а не только число ответов;
* **62% профилей скрыты** — Valve отдаёт вместо `account_id` заглушку
  `0xFFFFFFFF`. Видно в среднем **3.8 игрока из 10** (замер на 5000
  матчей, 49 992 слота). Отсюда прямое следствие для правила отбора:
  порог «минимум четыре известных ранга» недостижим в принципе, и
  опираться надо на два-три известных — матчмейкинг Dota однороден по
  рангу, так что двух известных Immortal уже достаточно.

Отдельно про откат на одиночные запросы: он делается **только** когда
пакет закрыт админски, то есть навсегда. Сбой пачки из-за квоты или сети
на одиночные НЕ откатывается — иначе один сбой превращается в полсотни
запросов и добивает лимит окончательно (случилось в первом прогоне).

Три состояния ранга различаются строго, и это не педантизм: отсутствие
строки — «не встречался», `NULL` — «встречался, не опрошен», `0` —
«опрошен, ранга нет». Слить последние два значило бы вечно опрашивать
закрытые профили и съесть всю квоту (ровно так задушил себя STRATZ в
спринте 87). По той же причине резолвер обязан различать «ответ получен,
ранга нет» и «запрос не удался»: первое пишется в кэш, второе — нет.

**Посев из архива (`ranks-harvest`) — первое, что надо запустить.** С
самого начала сбора мы складываем сырой JSON каждого матча в MinIO
(`RawMatchStore`, спринт 60), а в нём `rank_tier` лежит **у каждого
игрока**, не средним по матчу. Псевдонимизация PII хеширует ник, а не
`account_id`, поэтому идентификаторы целы. Это тысячи готовых пар
«аккаунт → ранг», уже оплаченных квотой, за ноль новых вызовов — и
именно высокоранговых, потому что такие матчи мы и отбирали.

Два правила посева, и оба неочевидны. Ранг записывается с датой МАТЧА, а
не сегодняшней: выдать ранг трёхмесячной давности за свежий значило бы
навсегда исключить его из очереди обновления. И свежий ответ никогда не
затирается архивным — условие в `ON CONFLICT`, — иначе повторный посев
откатывал бы кэш назад во времени.

Проверено, что ранга в самом реплее НЕТ: дамп схемы
(`DUMP_CLASS=CDOTA_PlayerResource`, а также `CDOTAPlayerController` и
`CDOTAGamerulesProxy`) не содержит ни одного поля про rank/medal/mmr.
Медаль рисуется по данным Game Coordinator, в поток сервера она не
попадает. Разбором реплея ранг не добыть — это не лечится своим парсером.

Приоритет опроса — по числу встреч в потоке. Аккаунтов миллионы, квоты
тысячи; опросить случайного игрока почти бесполезно, опросить того, кто
попадается каждый час, — значит распознавать его матчи всегда.

Главное число отчёта — **доля потока**: какой процент встреч приходится
на известных Immortal. Оно и решает, сколько матчей в сутки сможет
отобрать своя разбивка.

### Правило отбора и его замер (`ranks-scan`)

`ranks-scan` проходит по живому потоку Valve и считает, сколько матчей мы
бы взяли, ничего не скачивая. Печатает две вещи.

**Воронку по причинам** — сперва дешёвый отсев по полям, которые Valve уже
прислал (`не ранкед` / `не all pick` / `короткий`), и только потом ранги
(`мало известных рангов` / `низкий ранг` / `берём`). Порядок не
косметический: смешать «не наш режим» с «низкий ранг» значит лечить не ту
болезнь.

**Развёртку порогов** — долю потока при всех сочетаниях «сколько рангов
известно» × «какая доля из них Immortal». Порог на глаз мы уже выбирали
(`min_known=4` оказался недостижим при 3.8 видимых игроках), поэтому
теперь решение принимается по таблице.

Умолчание — **два известных ранга при доле 0.6**. Два, а не четыре,
потому что при 62% скрытых профилей четырёх известных не набрать у
половины матчей. Опора на двоих не так шатка, как кажется: матчмейкинг
Dota однороден по рангу, и два подтверждённых Immortal — сильное
свидетельство, что иммортален весь матч.

### Своя разбивка: очередь кандидатов (спринт 126)

`ranks-scan` не только считает, но и **складывает отобранные матчи в
очередь** (`ReplayCandidates`). Дальше их берёт отдельный коллектор:

```bash
# ~/manta-train.env
CANDIDATES_ENABLED=1        # без этого recover источник не поднимает
CANDIDATES_LIMIT=20         # матчей за цикл
CANDIDATES_INTERVAL=900     # секунд между циклами
```

```bash
make candidates-queue       # состояния очереди + выборка для проверки точности
```

Почему очередь в БД, а не в памяти: находим мы быстрее, чем качаем (один
вызов Valve отдаёт сто матчей, скачивание одного — 58 МиБ), и между
«нашли» и «скачали» лежат часы, перезапуски и суточные лимиты OpenDota.

**Сканер — это выборка, а не перечисление.** Мировой поток порядка
миллиона матчей в сутки, а Valve отдаёт около 2400 за проход и упирается
в 429. Читая подряд, сканер отставал бы примерно на две трети скорости
потока: курсор уезжает назад на ~0.7 дня за день работы, и недели через
три все кандидаты начали бы помечаться `expired` — реплеи живут около
двух недель. Ничего бы не сломалось, просто перестало бы работать.

Читать всё нам и не нужно: нужны полторы тысячи подходящих матчей в
сутки, а распределены они по потоку равномерно. Поэтому при отставании
свыше шести часов сканер **прыгает вперёд**, к живому краю. Отставание и
темп потока считаются бесплатно, по `start_time` уже прочитанных матчей —
ни одного лишнего вызова API. Прыжок обязательно подтверждается живым
ответом: перелёт за край оставил бы курсор в пустоте навсегда, потому
что пустой ответ неотличим от «догнали край».

Отставание печатается в каждом проходе (`отставание, ч`) — это главный
ранний симптом будущего простоя.

От OpenDota при этом остаётся ровно **одна** вещь — соль реплея. Список
матчей даёт Valve бесплатно, ранги приходят из кэша. Один запрос на матч
вместо прежних двух-трёх: суточная квота перестаёт быть потолком
датасета и становится потолком скачивания, который и так задан каналом.

Состояния кандидата: `new` → `taken` → `done`; `no_salt` — OpenDota так и
не отдал ссылку за 8 попыток; `expired` — реплея у Valve больше нет
(хранятся ~2 недели, поэтому у кандидата есть срок годности). Отсутствие
соли у свежего матча — **не ошибка**: она появляется с задержкой, матч
откладывается на 30 минут и возвращается в очередь.

Вместе с кандидатом сохраняется, ПОЧЕМУ он прошёл (сколько рангов было
известно, сколько из них Immortal, средний ранг). Это материал для
проверки точности правила: оно берёт матч по двум известным рангам из
десяти игроков, и такое допущение заслуживает проверки на данных, а не
доверия.

**Факт приезжает вместе с солью и стоит ноль.** Запрос `/matches/{id}`,
которым добывается `replay_url`, содержит `rank_tier` каждого игрока —
надо просто его не выбрасывать. Отсюда две вещи сразу.

Первая — `make candidates-queue` печатает **точность**: какая доля
игроков в скачанных матчах действительно оказалась Immortal. Знаменатель —
только матчи, где факт известен: NULL означает «не смотрели», и включать
такие значило бы разбавлять точность собственным незнанием.

Метрик рядом три, и это следствие ошибки. Первая версия считала матч
удачным при **среднем ранге ≥ 80**. Но у Immortal нет звёзд (ровно 80), а
Divine 5 — это 75, поэтому матч из восьми имморталов и одного дивайна
даёт 79.4 → 79 и шёл в брак. Критерий на деле означал «вообще все
Immortal» и на живых данных показал 79.3% при почти полном отсутствии
настоящего мусора. Теперь печатаются:

* **доля immortal** — средняя по матчам доля Immortal среди известных
  рангов; это и есть содержательная точность отбора;
* **все immortal** — прежний строгий критерий, оставлен для сравнения;
* **мусор** — матчи, где Immortal оказалось **меньше половины**. Бояться
  надо именно их: они означают, что правило ошиблось, а не что в составе
  был один дивайн.

Доля усредняется по матчам, а не по игрокам: пул по игрокам взвесил бы
матчи по числу известных рангов и начал бы мерить полноту данных
OpenDota вместо качества отбора.

Семантика живёт в SQL, поэтому у неё отдельная проверка на настоящем
Postgres — `make candidates-sql-test` (работает в своей схеме, рабочие
таблицы не трогает). Фейковый курсор такое не ловит: он возвращает то,
что в него положили, и любая подмена предиката проходит мимо.

Вторая важнее. Каждая закачка отдаёт до десяти пар «аккаунт → ранг»
прямо в кэш. При тысяче с лишним закачек в сутки это порядка десяти
тысяч рангов в день даром — больше, чем даёт вся суточная квота STRATZ.
А чем полнее кэш, тем выше доля отбора и тем больше кандидатов: петля
усиливает сама себя.

Про шкалу, чтобы не путаться при чтении отчёта: у Immortal **нет звёзд**,
поэтому `rank_tier` у всех ровно 80. Средний ранг 80 означает «все
известные — Immortal», а 78 — что среди них был кто-то ниже.

Отсутствие ранга при этом **не считается низким рангом**. Кэш заполняется
сверху вниз (посев из архива дал именно Immortal), поэтому «нет в кэше»
означает «ещё не спрашивали», и трактовать это как отказ значило бы
отбраковывать по собственному незнанию. Следствие: измеренная доля
отбираемого потока — оценка СНИЗУ, и она растёт по мере наполнения кэша.

### Потолки своей разбивки реплеев (замеры 2026-08-06)

Разбор — не ограничение: реплей 58 МиБ (zstd; Valve сменил формат с bz2,
не тронув расширение `.dem.bz2`) распаковывается за 0.4 с и разбирается
ядром `--deep` за 2.75 с, отдавая 111 632 события. Это порядка 27 000
матчей в сутки на одном ядре.

Ограничение — канал: 24–50 Мбит/с на одно соединение к CDN Valve, то
есть 1.4–2.8 часа закачки на каждую 1000 матчей и физический потолок в
несколько тысяч в сутки. Отсюда и нужен отбор ДО скачивания.

Чего у Valve нет и не будет: ранга (ни одного поля про rank/skill/mmr),
поминутных рядов (только итоги матча) и `replay_salt` — соль приходит
только из Game Coordinator, не из Web API.

### Бэкапы и автозапуск (Windows)

docker-volume — единственная копия датасета, и он уже терялся. Слепок с
ротацией (по умолчанию 7 дней, каталог `~/manta-backups`):

```bash
make backup                                  # разово
MANTA_BACKUP_DIR=/mnt/d/manta-backups make backup   # на диск Windows
```

Каталог на `/mnt/c`|`/mnt/d` переживает `wsl --unregister`. Сбой бэкапа
шлёт сообщение в Telegram (молча сломавшийся бэкап хуже отсутствующего);
старые слепки удаляются только после успешного нового.

**Оффсайт-копия в облако** (спринт 76). Локальный слепок лежит на диске
той же машины — переустановка системы уносит и датасет, и бэкап. Чтобы
копия жила вне машины, `backup.sh` после локального слепка заливает тот
же tar в облако через [rclone](https://rclone.org) (Google Drive, S3,
Dropbox — что настроите). По умолчанию выключено; включается одной
переменной. Отдельный планировщик не нужен — оффсайт едет на той же
ежедневной задаче `Manta-Backup`.

Слепок содержит никнеймы (PII), поэтому лить его в чужое облако в
открытом виде нельзя. Правильный способ — **crypt-ремоут rclone**:
шифрование на клиенте, облако видит только шифртекст.

```bash
# 1) поставить rclone
curl https://rclone.org/install.sh | sudo bash

# 2) настроить ремоут Google Drive (интерактивный OAuth в браузере)
rclone config          # → n, имя "gdrive", тип "drive", по подсказкам

# 3) обернуть его шифрованием (пароль запомнить — без него не расшифровать!)
rclone config          # → n, имя "gdrive-crypt", тип "crypt",
                       #   remote = gdrive:manta-backups

# 4) в ~/manta-train.env:
MANTA_CLOUD_REMOTE=gdrive-crypt:
```

После этого `make backup` (и ежедневная задача) заливают шифрованный tar
в Drive с той же ротацией `KEEP_DAYS`. Если `rclone` не установлен, а
`MANTA_CLOUD_REMOTE` задан — бэкап падает с ошибкой (не молча), локальная
копия при этом сохраняется. Сбой оффсайта — отдельный оранжевый алерт в
Telegram: локальный слепок цел, это деградация, а не потеря.

Восстановление на новой машине:

```bash
rclone copy gdrive-crypt: ~/restore/      # скачать последний слепок
make dataset-import IN=~/restore/manta-dataset-<дата>.tar
```

Автозапуск: из PowerShell **от администратора** (пути — свои):

```powershell
powershell -ExecutionPolicy Bypass -File \\wsl$\Ubuntu\home\<user>\manta\scripts\autostart-install.ps1
```

Создаст две задачи Планировщика: `Manta-Recover` (при входе в систему —
Docker Desktop, ожидание демона, `make recover`) и `Manta-Backup`
(ежедневно). Удалить: тот же скрипт с `-Uninstall`. Замечание: `dataset-export` НЕ переносит
`ReplayEvents` (combat-лог, под TTL) — для Death-Risk на объединённом
датасете нужно, чтобы реплеи парсились на той же машине, где потом
обучаешь, либо расширить экспорт.

## Производные: не кто богаче, а кто разгоняется (G1, спринт 131)

Первые 27 фич модели были **уровнями** — все до одной. Ни производной, ни
окна, ни «времени с момента». LightGBM обрабатывает поминутную строку
независимо и физически не может увидеть, растёт разрыв или схлопывается:
он знает, что Radiant впереди на 5000, и не знает, что минуту назад было
8000. Между «ведёт и разгоняется» и «ведёт, но теряет» модель не
различала ничего.

Косвенная улика, что это дорого: худший фазовый Brier — **ранняя игра
0.219** против 0.103 в поздней. Ранняя игра это ровно та фаза, где
текущее состояние говорит меньше всего, а направление движения — больше
всего.

Добавлено 15 фич: пять метрик (`networth_diff`, `xp_diff`, `towers_diff`,
`vision_coverage_diff`, `levels_diff`) на трёх окнах — 1, 3 и 5 минут
назад. Имена вида `networth_diff_rate_3m`, значение — изменение в минуту.

**Считается при чтении витрины, а не при сборе.** Оконные функции
ClickHouse прямо в `match_rows_sql`: миграции не нужно, пересбора не
нужно, значения появляются ретроактивно на всех уже собранных матчах.
Это ключевое отличие от трека F — те двенадцать фич писались в момент
сбора, у исторических матчей остались пустыми и потому не дали ничего.

Три решения, без которых число получилось бы неправильным:

* Кадр окна задан **в секундах игрового времени** (`RANGE`), а не в
  строках. Пропущенная минута — а на JSON-пути они встречаются — иначе
  молча превратила бы трёхминутное окно в четырёхминутное.
* Делится на **фактически прошедшее время**, а не на номинал окна. На
  второй минуте матча пятиминутного окна не существует; деление на номинал
  занизило бы темп впятеро ровно в той фазе, ради которой всё и делалось.
  Следствие, которое надо помнить: в начале матча все три окна совпадают.
* Окно **только назад** (`RANGE BETWEEN W PRECEDING AND CURRENT ROW`).
  Заглядывание вперёд — утечка целевой переменной: красивый Brier на
  валидации и мусор в проде, потому что в реальном матче будущего ещё нет.

Контракт производных лежит в **`libs/wp_rates.py`**, а не внутри
ml-service. Фичи модели считаются в двух местах: ml-service собирает
датасет сам, report-generator шлёт вектор по именам через gRPC. Списки уже
расходились дважды (спринты 90 и 91), и с производными расхождение было бы
хуже обычного — не падение, а **разные числа** у одной и той же модели в
обучении и в проде. Теперь оба сервиса берут оттуда и список, и SQL, и
формулу.

Монотонных ограничений у производных нет намеренно. Спринт вводит их,
чтобы ПРОВЕРИТЬ наличие сигнала; ограничение — доменное утверждение,
заданное заранее, и окажись оно неверным, абляция показала бы
«бесполезно», а мы не отличили бы неработающую идею от неверной
гипотезы, которой связали модель.

Вердикт выносит абляция, и группы разделены под два разных вопроса:

```bash
make ml-ablation            # G1_производные_все + G1_окно_1мин/3мин/5мин
```

`G1_производные_все` отвечает, несут ли производные сигнал вообще; три
семейства окон — какое именно работает. Скорее всего работает одно из
трёх: мерить их скопом значило бы утопить сработавшее в двух
несработавших. Правило волны действует — не давшее значимого улучшения
семейство удаляется, а не откладывается.

## Как читать `make ml-ablation` (спринт 132)

Абляция отключает группу фич (обнуляет в NaN), переобучает модель по тому
же протоколу и сравнивает парным бутстрапом по матчам. **Δ = Brier(без
фичи) − Brier(со всеми); Δ > 0 значит фича полезна.**

В отчёте два Δ, и это не украшение, а исправление ошибки измерения.

Фича, заполненная у 30% строк, физически не может двигать метрику на
остальных 70% — там модель её не видела ни с ней, ни без неё. Считая Δ по
всей валидации, инструмент **делил реальный эффект на долю покрытия**:
честные 0.003 на своей подвыборке превращались в 0.001 общего и попадали
ровно в порог «практической пользы нет». Занижение тем сильнее, чем реже
фича, — то есть ревизия трека F старым инструментом выкинула бы именно те
фичи, ради проверки которых она затевалась.

| колонка | что означает |
|---|---|
| **Δ где есть** | только строки, где фича заполнена. **По нему выносится вердикт**: работает ли фича там, где она есть |
| **Δ везде** | вся валидация: масштаб продуктового эффекта сегодня |

Оговорка: подвыборка не случайна — реплейные матчи отличаются от
JSON-матчей, — поэтому «где есть» это эффект на популяции матчей с полным
сигналом, а не на всём датасете.

Ниже основной таблицы — **Δ по фазам игры**. Объективы (Рошан, аегис,
бэйбеки) живут в поздней игре, производные трека G — в ранней; фича,
дающая много в одной фазе и ноль в остальных, в агрегате выглядит шумом.
Звёздочка означает, что на этой фазе эффект превышает 2σ.

Отложенные вердикты («вернуться при росте данных») печатаются с числом
**матчей**, несущих сигнал. Доля строк на вопрос «насколько ещё вырасти»
не отвечает: 5% строк — это и сто матчей, и пять.

Поведение самих окон проверяется на живом ClickHouse:

```bash
make wp-rates-sql-test      # окно назад, кадр в секундах, без протечки между матчами
```

## Наблюдаемость без Docker/Grafana

Каждый сервис отдаёт Prometheus-метрики на своём порту:

| Порт | Сервис | Порт | Сервис |
|---|---|---|---|
| `9101` | parser-svc | `9104` | ml-service (gRPC) |
| `9102` | feature-extractor | `9105` | data-collector |
| `9103` | report-generator | `9106` | ml-autotrain |

Посмотреть, что реально слушает порты: `sudo ss -tlnp`. Сырые метрики
сервиса: `curl -s localhost:9106/metrics`.

Живой дашборд без установки чего-либо (только python3) — собирает метрики
всех сервисов серверно (обходит CORS браузера), плюс число матчей прямо из
ClickHouse; авто-обновление, спарклайны, статус up/down, тёмная/светлая тема:

```bash
make dashboard        # http://localhost:9107
```

`scripts/dashboard.py` — один файл на стандартной библиотеке; порты можно
переопределить (`DASHBOARD_PORT`, `*_METRICS_PORT`). Инфраструктурные порты:
ClickHouse `8123` (HTTP) / `9000` (native), Kafka `9092`, Postgres `5432`,
Redis `6379`, MinIO `9500` (S3) / `9501` (веб-консоль).
