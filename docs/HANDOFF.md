# Manta — сводка для нового чата (обновлено 2026-07-27, после спринта 75)

Manta — платформа аналитики Dota 2: сбор матчей → парсинг реплеев →
фичи → ML-модели (Win Probability, Death-Risk) → отчёты с разбором
ошибок → веб-UI. Монорепо `unmekeed/manta`, ветка `main`, всё в
коммитах по спринтам (1–75). Спецификация — `docs/specification/`,
роадмап — `docs/ROADMAP.md`, инциденты — `docs/runbooks.md`.

**Ключевой операционный факт**: облачный сбор ОСТАНОВЛЕН (решение
владельца, 2026-07-19). Локалка (Windows + WSL2 + Docker Desktop,
`~/manta`) — единственный источник истины: сбор, обучение,
Telegram-уведомления. Облачная песочница используется только для
разработки кода; её docker-volumes эфемерны и уже откатывались,
а git-чекаут в ней после перезапуска среды может оказаться СТАРЫМ —
первым делом всегда `git fetch origin main && git merge --ff-only`.

## Архитектура (все сервисы — процессы на хосте поверх docker-инфры)

```
OpenDota API ──► data-collector (4 процесса-источника, Python)
   │  реплей-путь: .dem → MinIO → Kafka(match.downloaded)
   │  JSON-путь:   таймлайны → ClickHouse напрямую (без реплея)
   ▼
parser-svc (Go + C++ ядро demoinfo) — Kafka → разбор .dem →
   ReplayEvents / EconomyTimeline / PositionSnapshots (ClickHouse)
   → Kafka(replay.parsed); .dem после парсинга удаляется
   ▼
feature-extractor (Python) — сырые таблицы → витрины
   PlayerMatchFeatures / MatchTimelineFeatures → Kafka(features.calculated);
   при FEATURE_STORE_ADDR пушит последний срез в Feature Store
   ▼
ml-service (gRPC :50051) — Predict/PredictStream; модели из реестра;
   model_name маршрутизируется: win_probability | death_risk
report-generator — Kafka-петля + CLI --match: WP-кривая через
   PredictStream (SHAP-вклады), атрибуция ошибок ΔWP, модельный SI,
   позиции смертей → MatchReports (Postgres, jsonb)
auto-train (training.auto) — переобучение WP по объёму (+20 матчей)
   или PSI-дрейфу; честный гейт на общем holdout; Telegram-уведомления;
   алерт «витрина не растёт» (DATASET_STALL_ALERT_H=12)
api-gateway (Go :8080) — REST: /matches, /timeline, /analysis,
   /heroes, /draft/simulate (gRPC-прокси к Draft)
frontend (React+TS+Vite) — список матчей, матч (WP beta-бейдж,
   SHAP-чипы, карта смертей, риск-бейджи), драфт-симулятор
Similarity (:50052) / Draft (:50053) / Coach (:50054) /
   Feature Store (:50055, Redis) — gRPC-сервисы поверх витрин
```

Инфраструктура (docker compose, `deployments/docker-compose.yml`):
Postgres 16 (:5432, БД manta + mlflow), ClickHouse 24.8 (:8123/:9000),
Kafka 3.8 (:9092, **AUTO_CREATE_TOPICS=false — топики только через
`make topics`!**), MinIO (:9500/:9501, бакеты replays+models), Redis
(:6379), MLflow (:9600, backend в postgres). Креды dev: dota /
dota_dev_password. Метрики Prometheus: 9101–9114; живой дашборд —
`make dashboard` (:9107).

## Данные

- Postgres: collectedmatches (дедуп сбора), collectorcursor,
  matchreports (готовые отчёты jsonb), eventoutbox и др.
- ClickHouse (manta): ReplayEvents (**TTL 14 дней**), EconomyTimeline,
  PositionSnapshots (**player_id НЕ заполняется — сущность = hero,
  ростер и команды брать из PlayerMatchFeatures**), PlayerMatchFeatures,
  MatchTimelineFeatures (витрина WP: ReplacingMergeTree, читать FINAL),
  **MatchDraft** (1 строка = матч: составы, баны, патч, draft_prior) и
  **MatchEvents** (roshan/aegis/firstblood/buyback/rune/ward_* — из
  того же JSON, миграция 011). Витрина с миграции 012 несёт 12 новых
  поминутных колонок (DEFAULT nan) — см. «Трек F» ниже.
- **MinIO `matches-json`**: сырой JSON каждого матча, gzip, ключ
  `{match_id//1_000_000}/{match_id}.json.gz` (~50–150 КиБ). Смысл —
  любая будущая фича бэкфиллится без единого вызова OpenDota.
  Выключается `RAW_MATCH_STORE=0`. Пишется с момента спринта 60,
  поэтому для 2635 более старых матчей сырья нет и не будет.
- Матчи двух путей: реплейные (полные: позиции/SI/laning) и JSON
  (только таймлайн, NaN в позиционных фичах). Tier: Premium
  (высокий ранг) / Professional (про-эталон гейта, в train не входит).
- Реестр моделей: S3 (MinIO) по умолчанию, REGISTRY_BACKEND=mlflow —
  опция; авточистка REGISTRY_KEEP_LAST=10 + все продвигавшиеся.
- **Параллельный сбор на 2+ машинах** (разные IP = разные квоты
  ~3000/сутки): COLLECTOR_SHARD_COUNT/COLLECTOR_SHARD_ID в env-файле
  (одинаковый COUNT, разный ID) — шардирование match_id % N, пересечений
  нет, dataset-import конфликт-фри. Реализовано в sources/Shard.
- `make dataset-export` / `dataset-import IN=…tar` — перенос между
  машинами, идемпотентно. **Слепок НЕ включает ReplayEvents** (TTL,
  объём) — после импорта позиции есть, а combat-лога нет; Death-Risk
  на новой машине требует локально спарсенных реплеев.

### Темп сбора и бюджет квоты (2026-07-26)

Решение владельца: выбирать квоту почти целиком, чтобы быстрее набрать
матчи с сигналами трека F (без них ревизия F2–F6 невозможна — см. ниже).
Настройки живут в `~/manta-train.env`, recover читает их через `set -a`:

```
TIMELINE_LIMIT=14        # было 10
PRO_TIMELINE_LIMIT=4     # было 5
OPENDOTA_LIMIT=2         # было 1 (реплейный public; pro-replay захардкожен в 1)
```

**Как считается бюджет** — это неочевидно и раньше считалось неверно.
Таймлайн-источник тратит НЕ один вызов на матч: `detail_budget = 2 ×
limit_per_cycle`, потому что фильтры качества (ranked/All Pick, ≥15 мин,
патч, rank_tier ≥ 80) отбраковывают примерно половину кандидатов с
вершины /parsedMatches. Плюс 1–2 вызова списка на цикл. Итого:

| Коллектор | Цикл | Вызовов/сутки (макс) | Матчей/сутки |
|---|---|---|---|
| opendota-timeline | 30 мин, limit 14 | ~1440 | до 672 |
| opendota-timeline-pro | 60 мин, limit 4 | ~216 | до 96 |
| opendota-public (реплеи) | 60 мин, limit 2 | 72 | 48 |
| opendota (pro-реплеи) | 60 мин, limit 1 | 48 | 24 |
| **итого на машину** | | **~1780** | **~840** |

Две машины = два IP = две квоты, суммарно ~1700 матчей/сутки. Burst-лимит
60/мин не задет: между вызовами пауза 1.1 с (~54/мин).

Прежние дефолты давали ~1400 вызовов/сутки, а не «1100–1200», как
говорил комментарий в dev-recover.sh: он не учитывал множитель 2 в
detail_budget. Комментарий исправлен.

**Риск (инцидент №3).** Реальный дневной лимит ниже заявленного;
при 429 коллектор спит до 00:00 UTC, а не до следующего цикла. Симптом
перебора — витрина растёт только в окно 4–7 утра МСК. Контроль:

```bash
grep -c "429\|rate limit" ~/manta-logs/timeline.log
make doctor | grep remaining-day
```

Ушло в минус или есть 429 → `TIMELINE_LIMIT=12`. Сутки без 429 → можно 16.

**Потолок комбат-лога.** У ReplayEvents TTL 14 дней, поэтому в окне
держится 14 × (реплеев в сутки). При limit 2 + pro-реплеи это ~1000
матчей — уже сопоставимо с облачным обучением Death-Risk (1482), но всё
ещё не с запасом. Больше реплеев — это трафик: ~75 МиБ на матч,
3 реплея/час ≈ 5.4 ГиБ/сутки.

## Модели

- **Win Probability** v0.8.0: LightGBM + OOF-изотоника, **22 фичи**
  (было 10; +12 из трека F, все с DEFAULT nan).
  Гейт: про-эталон/fresh-holdout на общих данных + бутстрап-σ.
  OOF-Brier ~0.137–0.144, про-эталон 0.15–0.16, фазовые Brier
  early ~0.22 / mid ~0.13 / late ~0.09. Критерии релиза B1+B2 пройдены.
  **Важно: v0.8.0 не лучше v0.7 по метрике** — новые фичи пусты на
  историческом датасете (см. «Трек F» ниже), это задел, а не выигрыш.
- **Draft Prior** (спринт 62, `training/draft_prior.py`,
  `make ml-train-draft`): P(win | составы, патч) на пер-матчевых
  строках MatchDraft. AUC 0.5846, Brier 0.23846 против константы
  0.24336 (1482 матча). OOF-прайоры (`oof_priors`, 5 фолдов) пишутся
  в MatchDraft.draft_prior и попадают в витрину как фича WP.
  **Парные фичи (synergy/matchup) отключены** `select_features()`
  до `PAIR_MIN_OBS=8` наблюдений на пару — на 1482 матчах и 127 героях
  их «сигнал» был чистой утечкой (см. хронику №15).
- **Death-Risk** v0.1.0 (спринт 48): P(смерть героя в 30с) по 9
  позиционным фичам. training/risk.py; GroupSplit ПО МАТЧАМ (row-split
  = утечка); дедуп снапшотов по тику (иллюзии пересэмплируют драки).
  Облачное обучение: 1482 матча / 3.65M сэмплов, AUC 0.792, PR-AUC
  0.302 (×3.3 к базе 9.1%), Brier 0.072. Сервится тем же классом, что
  WP (одинаковый формат артефакта); Predict(model_name="death_risk").
  В отчётах заменяет эвристический SI (поле si_model=true, порог
  «рискованно» 0.3; фолбэк на эвристику, порог 0.6).
  **На локалке обучить свою**: `make ml-train-risk RISK_ARGS="--push"`
  (нужны ReplayEvents — см. хронику инцидентов №6).
- **Laning** v0.1.0 (спринт 50, C5 закрыт целиком): P(линия выиграна к
  10-й, метка lane_nw_diff_at_10>0) по игре ПЕРВЫХ 5 минут — lh/dn@5,
  урон по героям/от героев, kills/deaths (combat-лог ReplayEvents),
  is_mid. training/laning.py; GroupSplit по матчам (исходы линий одного
  матча связаны). Облачное обучение: 1482 матча / 14.4K строк, AUC
  0.886, brier_skill 0.47 (спека 6.3.2 просит R² — это его аналог для
  вероятностной постановки). Predict(model_name="laning"); в отчётах
  заменяет сигмоид-эвристику laning_score (поле laning_model=true;
  roam/без combat-лога — фолбэк на эвристику). Обучить:
  `make ml-train-laning LANING_ARGS="--push"` (те же ReplayEvents под
  TTL — датасет только из свежих реплейных матчей).

## Хроника инцидентов и уроки (все случились реально)

1. **Эфемерность облачной среды** — контейнер перезапускается, dockerd
   и фоновые процессы гибнут, docker-volumes могут ОТКАТИТЬСЯ на
   старый снапшот, git-чекаут — на старый коммит. Решение:
   `make recover` идемпотентен; в облаке начинать с git fetch/merge.
   Нюанс recover: nohup-дети держат родительский bash (скрипт «висит»
   в do_wait) — это косметика, процессы уже запущены.
2. **ClickHouse после нечистого стопа**: стартует минуты (разгребает
   tmp-мерджи), в контейнере ulimit 4096 → «Too many open files» и
   зацикленный мердж system.metric_log. Ждать «Ready for connections»;
   при зацикливании — docker restart clickhouse.
3. **Квота OpenDota (анонимная)**: реальный дневной лимит НИЖЕ
   заявленного (remaining-day уходил в −930); сброс 00:00 UTC. Симптом:
   рост матчей только в окно ~4–7 утра МСК. Решения по слоям: бюджетные
   дефолты recover (до ~1400 вызовов/сутки — не «1100», см. «Темп сбора»
   выше про множитель 2 в detail_budget), кэш отвергнутых кандидатов,
   TIMELINE_DETAIL_BUDGET, при 429 — сон до 00:00 UTC (не interval!),
   отдельный лог с remaining-day + метрика opendota_rate_limited_total.
   OPENDOTA_API_KEY поддержан кодом (сайт ключей периодически лежит).
   С 2026-07-26 темп поднят до ~1780/сутки решением владельца (E4) —
   это осознанно близко к потолку, поэтому 429 надо мониторить.
4. **«Telegram-уведомления прекратились»** = чаще всего датасет
   перестал расти (auto-train шлёт только при переобучении). Смотреть
   не на бота, а на рост витрины по часам. Облако слать не может
   вообще (нет MANTA_TRAIN_ENV) — источник сообщений не путать.
5. **Рестарт Docker Desktop**: контейнеры пересоздаются, а хост-процессы
   остаются жить со СТАРЫМИ соединениями — pgrep «OK», но каждый цикл
   падает psycopg.OperationalError. Решено в коде (спринт 47:
   _ensure_db ping+reconnect в обоих раннерах). rdkafka реконнектится
   сам. На старом коде: pkill коллекторов + make recover.
6. **Потеря Kafka-топиков** (volume пересоздался; AUTO_CREATE=false):
   продюсер МОЛЧА теряет сообщения (ошибка приходит асинхронно, flush
   не спасает; rdkafka пишет «Terminating with 1 message in queue» при
   --once), консьюмер-группы не создаются, реплейный путь мёртв
   НЕДЕЛЯМИ — незаметно, потому что JSON-путь продолжает наполнять
   витрину. Итог на локалке: ReplayEvents никогда не наполнялась
   (PositionSnapshots была — из dataset-import). Диагностика:
   `kafka-topics.sh --list` (только __consumer_offsets = беда),
   `kafka-consumer-groups.sh --describe --group replay-parser`
   (group id — replay-parser, НЕ parser-svc); пустая таблица vs
   вычищенная TTL: system.parts + min(ingested_at)=1970 → parts
   никогда не было. Лечение: make topics; перезапуск parser-svc и
   extractor; системное решение — спринт 49 (ниже).
7. **Непрогнанная миграция** (009 networth_total): similarity падал
   404/UNKNOWN_IDENTIFIER. После каждого git pull — make migrate.
8. **Логи в /tmp гибнут** при рестарте WSL — истории для диагностики
   нет. Решено в спринте 49: MANTA_LOG_DIR по умолчанию ~/manta-logs.
9. **Порт-коллизии**: 9113 заняли и coach, и feature-store (стор
   переехал на 9114); «Address already in use» у ml-service — это
   НАМЕРЕННО (so_reuseport=0), чтобы задвоенный сервер со старой
   моделью не отвечал молча — убить старый процесс.
10. **PositionSnapshots.player_id = 0 всегда** — группировать по hero,
    команды из PlayerMatchFeatures (team 2/3). Иллюзии дают несколько
    строк героя на тик.
11. **Часы WSL2 могут дрейфовать** после сна (в нашем случае не
    подтвердилось, но проверка времени контейнеров vs хоста — полезный
    пункт диагностики; лечение: wsl --shutdown из PowerShell).
12. **Файлы >30 МиБ** через чат не проходят — резать: split -b 25M,
    собирать: cat parts > file (Windows: cmd /c copy /b).
13. **CH-миграция 002 стирала ReplayEvents на КАЖДОМ recover** (спринт
    54): 002 делает `DROP TABLE IF EXISTS ReplayEvents` (одноразовая
    правка схемы), а migrate-ch прогонял все файлы каждый recover — combat-
    лог обнулялся при каждом запуске. PositionSnapshots/EconomyTimeline/
    витрина создаются через IF NOT EXISTS без DROP — уцелевали, поэтому
    терялся именно ReplayEvents (обучение Death-Risk/Laning, атрибуция
    ошибок). Симптом: сразу после recover doctor «ReplayEvents ПУСТА» при
    живом parser-svc и непересозданном контейнере ClickHouse. Решение:
    CH-миграции получили журнал manta.SchemaMigrations (scripts/ch-migrate.sh),
    как PG в спринте 49 — каждый файл ровно один раз.

14. **`docker exec -i` + INSERT = вечное зависание** (спринт 54→58):
    clickhouse-client, увидев INSERT при не-TTY stdin, читает секцию
    данных ИЗ STDIN. С флагом `-i` recover замирал на записи в журнал
    миграций — молча, без таймаута. В песочнице не воспроизводилось:
    там stdin закрыт и клиент сразу получает EOF, а в интерактивном
    терминале EOF не приходит никогда. Лечение: `q()` вызывает
    `docker exec` БЕЗ `-i` и с `</dev/null`; `-i` остаётся только там,
    где файл миграции реально подаётся на stdin. Урок: скрипты,
    работающие в CI/песочнице, обязательно проверять с ОТКРЫТЫМ stdin.

15. **Утечка в парных фичах драфта** (спринт 62): synergy/matchup
    (винрейт пары героев) давали внутривыборочную корреляцию с исходом
    0.835 и 0.896 — выглядело как прорыв. Честный OOF-AUC при этом был
    **0.502**, то есть монетка. Причина арифметическая: 127 героев →
    ~8000 пар, при 1482 матчах на пару приходится <1 наблюдения, и
    «винрейт пары» = исход того самого матча, переписанный в фичу.
    Лечение: `select_features(n_matches, n_heroes)` включает парные
    фичи только при ≥`PAIR_MIN_OBS=8` наблюдений на пару; регресс ловит
    тест `test_oof_prior_does_not_memorise_outcome` (на данных БЕЗ
    сигнала прайор обязан не коррелировать с исходом). Урок: любую
    фичу-агрегат по истории считать OOF, а «слишком хорошую» корреляцию
    считать симптомом, а не победой.

16. **Расширение FEATURES ломает всё, что знает про их число** (спринт
    61–65, 10→22): падало `IndexError: index 10 is out of bounds` в
    synth_matches и `Length of feature_name(22) and num_feature(10)
    don't match` в LightGBM. Тестовые векторы были захардкожены.
    Лечение: `synth_matches` добивает строки NaN до `len(FEATURES)`,
    в тестах вектор строится ИЗ `FEATURES` (`_pad()`, `fv()`).
    Правило: никогда не писать в тесте литеральный вектор фич.

17. **`make recover` не обновляет код живых процессов**: он стартует
    сервис только если тот ещё не жив (`if ! pgrep`), поэтому после
    `git pull` всё остаётся на прежней версии — при полностью зелёном
    doctor. Лечение: `make stop` (scripts/dev-stop.sh, спринт 67) перед
    pull; порядок в runbooks §5. Там же — почему модель отдельно
    останавливать не нужно, а вот читателей фич обновлять обязательно.

18. **Читатели витрины отставали от FEATURES** (найдено при подготовке
    инструкции по обновлению): report-generator строил словарь фич из 10
    захардкоженных имён, а ml-service требует ВСЕ имена из
    model.features. Пока в production 10-фичный v0.7 — работает; в
    момент, когда гейт продвинул бы 22-фичный v0.8 (auto-train делает
    это сам), каждый Predict отвечал бы INVALID_ARGUMENT и генерация
    отчётов встала бы целиком. Та же болезнь была у CLI
    predictors.wp_curve и explain (читали 10 колонок → модель получала
    NaN вместо реальных значений). Лечение: единый
    `training.dataset.match_rows_sql`/`ROW_COLUMNS` в ml-service,
    `WP_PASSTHROUGH_FEATURES` в report-generator и тест-страж
    `test_wp_features_sync.py`, сверяющий два списка. Урок: при

- **Спринт 98 — агрегат тепловых карт `MatchMapCells`**: сетка 32×32 в
  разрезе «фаза × сторона × слой», шесть слоёв — presence, farm, death,

  килобайт на матч против сотен и **без TTL**.

  * **ReplacingMergeTree, не SummingMergeTree.** Переразбор матча должен
    ЗАМЕЩАТЬ клетки. Суммирующий движок удвоил бы плотность при каждом
    повторе, и карта врала бы тем сильнее, чем чаще матч обрабатывали, —
    причём выглядела бы при этом нормально.
  * **Фазы по игровому времени, не по доле матча.** 10-я минута значит
    одно и то же в игре на 25 и на 60 минут; «первая треть» — нет.
  * **Координаты нормализуются при записи.** Хранить игровые единицы
    значило бы, что смена системы координат у поставщика молча сдвинет
    всю историю.
  * **`cell()` отбрасывает точки вне карты и NaN.** Прямое следствие
    спринта 97: без проверки вся карта смертей собралась бы в одну
    центральную клетку и выглядела бы правдоподобно.
  * **Сторона смерти — погибшего, варда и смоука — поставившего.**
    Перепутать значило бы получить карту, зеркальную по сторонам, и
    заметить это было бы почти нечем. Закреплено тестами.
  * **`farm` — не отдельный источник, а присутствие живого героя без
    врага в радиусе `FIGHT_R`.** Это и отличает фарм-маршрут от маршрута

  именами героев, а я искал по нормализованным — в бою карта вышла бы
  пустой и выглядела бы как «матч без событий». Ключи нормализуются один

  76, где `MatchDraft`/`MatchEvents` завели, а в слепок внести забыли, и

  сообщении. Зависимость `zstandard` добавлена в requirements
  data-collector — recover ставит её сам (штамп по хэшу файла).
  Мораль на будущее: расширение файла — не источник истины о его
  формате, а диагностическое сообщение обязано содержать сырые данные,
