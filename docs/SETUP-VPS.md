# Manta на VPS

Развёртывание на публичной машине. Отличий от домашней установки
(`docs/SETUP-WSL.md`) три, и все три — про то, что у машины белый адрес:
пароли, порты и отсутствие браузера.

---

## 0. Чем VPS отличается от домашней машины

| | Дома (WSL) | VPS |
|---|---|---|
| Сервисы | процессами на хосте (`dev-recover.sh`) | в Docker (профиль `apps`) |
| Пароли | дев-умолчание из репозитория | генерируются при установке |
| Порты | открыты, машина за NAT | только `127.0.0.1` + SSH-туннель |
| Grafana | браузером на localhost:3001 | через туннель |
| Телеметрия | дашборд под рукой | Telegram-сторож раз в сутки |

Про пароли стоит сказать прямо. Базовый `docker-compose.yml` до спринта
143 содержал `dota_dev_password` литералами — то есть пароль лежал в
публичном git. Дома за NAT это безвредно, на VPS — нет. Теперь compose
берёт пароль из окружения, а дев-умолчание остаётся для домашней машины:

```yaml
POSTGRES_PASSWORD: ${MANTA_DB_PASSWORD:-dota_dev_password}
```

Нет переменной — работает как раньше. Есть — работает на настоящем
пароле. Домашнюю установку это не задевает совсем.

---

## 1. Требования к машине

Проверено на Ubuntu 24.04.

| Ресурс | Минимум | Почему |
|---|---|---|
| RAM | 8 ГБ | ClickHouse + Kafka + Postgres + MinIO; потолки прописаны в `docker-compose.vps.yml` |
| Диск | 60 ГБ | датасет растёт; реплеи не хранятся (`PURGE_PARSED_REPLAYS=true`) |
| CPU | 2 ядра | разбор реплеев упирается в CPU, но он не обязателен на VPS |

Если машина мощнее — потолки памяти в наложении считаются от
`TARGET_RAM_MB`, их стоит поднять.

## 2. Установка

```bash
sudo apt update && sudo apt install -y git
git clone https://github.com/unmekeed/manta.git ~/manta
cd ~/manta
./scripts/vps-bootstrap.sh
```

Скрипт **идемпотентен**: гонять повторно можно и нужно — после сбоя,
после `git pull`, просто чтобы свериться. Посмотреть, что он сделает, не
делая:

```bash
./scripts/vps-bootstrap.sh --check
```

Что он делает по порядку: генерирует пароли → ставит Docker → включает
фаервол (наружу только SSH) → проверяет занятость портов → собирает
образы по одному → поднимает стек с наложением для VPS → применяет
миграции → проверяет, что контейнеры живы → заводит расписание.

Пересборка образов входит в прогон, и это важно после `git pull`:
изменения в `requirements.txt` или Dockerfile живым контейнерам не видны,
их надо запечь. Поэтому обновление — всегда два шага, а не `restart`:

```bash
cd ~/manta && git pull origin main
./scripts/vps-bootstrap.sh
```

### Какие коллекторы поднимаются

Те же семь источников, что дома поднимал `dev-recover.sh` — это
проверяется тестом, сверяющим compose с ним построчно:

| Сервис | Источник | Когда |
|---|---|---|
| data-collector | opendota-public | всегда |
| timeline-collector | opendota-timeline | всегда |
| pro-timeline-collector | opendota-timeline-pro | всегда |
| league-collector | opendota-league | всегда |
| pro-replay-collector | opendota | всегда |
| stratz-collector | stratz-timeline | если задан `STRATZ_API_TOKEN` |
| candidates-collector | candidates | если `CANDIDATES_ENABLED=1` |

Два последних — в отдельных профилях, и bootstrap включает их по тем же
признакам, что и дом. Не по прихоти: STRATZ без токена падает на старте,
а `restart: unless-stopped` превратил бы это в ровный шум в логах —
поломку, неотличимую от работы.

### Про пароль — единственное место, где легко потерять данные

Пароль генерируется **один раз** и кладётся в `deployments/.env` (0600).
Повторный прогон его не трогает, и это не перестраховка: тома Postgres и
ClickHouse созданы с этим паролем. Сгенерируй новый — контейнеры
перестанут пускать к уже собранным данным, а выглядеть это будет как
«база сломалась».

Тот же пароль дописывается в `~/manta-train.env`, потому что скрипты на
хосте (бэкап, миграции, обмен) ходят в контейнеры напрямую. Два файла,
один пароль. Если они разъедутся, ошибка будет не «отказ», а «пароль
неверен» из бэкапа при живом контейнере.

## 3. Что дописать руками

`nano ~/manta-train.env` — метка машины, шард и ключи:

```
MANTA_HOST_LABEL=vps

# Темп сбора
TIMELINE_LIMIT=14
PRO_TIMELINE_LIMIT=4
OPENDOTA_LIMIT=2
LEAGUE_LIMIT=12

# STRATZ (коллектор поднимается ТОЛЬКО при заданном токене)
STRATZ_API_TOKEN=
STRATZ_LIMIT=400
STRATZ_INTERVAL=2100
STRATZ_DETAIL_BUDGET=200
STRATZ_BATCH_SIZE=1

# Своя разбивка (качает 58 МиБ на матч — включать осознанно)
CANDIDATES_ENABLED=1
STEAM_API_KEY=

OPENDOTA_API_KEY=
TELEGRAM_BOT_TOKEN=
TELEGRAM_CHAT_ID=

MANTA_CLOUD_REMOTE=gdrive-crypt:manta-backups
```

**Про шардирование: пока VPS — единственный сборщик, его быть не должно.**
`COLLECTOR_SHARD_ID` и `COLLECTOR_SHARD_COUNT` не задаются вовсе, работают
умолчания (0 из 1, то есть «беру всё»). Шард нужен только тогда, когда
машин-сборщиков несколько, и поднимать `COLLECTOR_SHARD_COUNT` надо на
всех разом: забыть одну — она продолжит качать свою долю, а чужую не
заберёт никто.

Метка обязана отличаться от домашних: по ней машины узнают свои слепки
в облаке.

**Чего здесь быть не должно.** `STEAM_BOT_PASSWORD` — пароль от аккаунта
Steam. Он нужен ровно один раз, для `make gc-token`, который меняет его
на refresh-токен; после этого строку стоит стереть. Держать пароль на
машине с белым адресом незачем.

**После правки файла перезапустите стек:**

```bash
./scripts/vps-bootstrap.sh      # он идемпотентен и подхватит новые значения
```

Это не формальность. На VPS сервисы живут в Docker, а `~/manta-train.env`
читают только скрипты на хосте — контейнеры его не видят. Значения
попадают в них через окружение `docker compose`, и загружает их
`vps-bootstrap.sh` перед подъёмом стека. Отредактировать файл и не
перезапустить — значит оставить коллектор с шардом по умолчанию (0 из 1,
«беру всё»), то есть собирать те же матчи, что домашние машины. Отказа не
будет: только удвоенная работа и сожжённая квота.

Проверить, что доехало:

```bash
docker exec manta-data-collector-1 printenv | grep -E 'SHARD|API_KEY'
```

Telegram здесь важнее, чем дома: браузера на VPS нет, и сторож —
единственная телеметрия, которая доходит сама.

## 4. rclone

OAuth Google Drive требует браузера, которого на VPS нет. Поэтому конфиг
переносится с домашней машины:

```bash
# дома
rclone config file          # покажет путь, обычно ~/.config/rclone/rclone.conf
scp ~/.config/rclone/rclone.conf vps:~/.config/rclone/rclone.conf
```

```bash
# на VPS
chmod 600 ~/.config/rclone/rclone.conf
rclone lsf gdrive-crypt:manta-backups | head
```

Файл содержит ключи шифрования crypt-ремоута. Потеряете его — облачные
бэкапы не расшифровать ничем; храните копию отдельно от обеих машин.

## 5. Датасет

Пустой стек работоспособен — сбор наполнит его сам, но модель без данных
не обучится.

Пока модели нет, `ml-service` **поднимается и работает**: метрика
`ml_model_loaded` держит 0, а запросы получают `UNAVAILABLE` с внятным
текстом. Раз в минуту он заглядывает в реестр и подхватит модель сам,
как только `ml-autotrain` её опубликует — перезапускать ничего не надо.
До спринта 145 пустой реестр ронял сервис на старте, и нормальное
состояние свежей машины выглядело как поломка.

Быстрый путь к данным: забрать слепок домашней машины через тот же обмен.

```bash
make peer-sync ARGS=--dry-run   # посмотреть, что найдётся
make peer-sync                  # втянуть
```

Дальше обмен идёт по расписанию сам.

## 6. Доступ к панелям

Наружу не смотрит ничего. Grafana, MinIO и прочее — через SSH-туннель с
домашней машины:

```bash
ssh -N -L 3001:127.0.0.1:3001 -L 8123:127.0.0.1:8123 vps
```

Дальше `http://localhost:3001` в домашнем браузере. Пароль Grafana лежит
в `deployments/.env` (`GRAFANA_ADMIN_PASSWORD`).

Проверить, что снаружи действительно ничего нет, — **с другой машины**, а
не с самой VPS:

```bash
nmap -Pn <адрес-vps>        # ожидаем только 22/tcp
```

## 7. Расписание

`vps-bootstrap.sh` заводит три задачи (время в UTC):

```
30 3 * * *  backup.sh      свой слепок + выгрузка в облако
0  4 * * *  peer-sync.sh   втянуть слепки других машин
0  9 * * *  heartbeat.sh   одно сообщение в Telegram
```

Порядок не случаен: сначала опубликовать своё, потом забрать чужое, потом
доложить. Сторож шлёт сообщение **каждый** прогон, а не только при сбое —
поэтому его отсутствие само становится сигналом.

---

## 8. Проверка после установки

```bash
./scripts/vps-bootstrap.sh --check
make doctor
make heartbeat            # должно прийти сообщение в Telegram
docker compose -f deployments/docker-compose.yml \
               -f deployments/docker-compose.vps.yml ps
```

`make doctor` первые сутки будет ругаться на свежесть данных — сбор ещё
не набрал глубину. Это норма; тревожно, если он ругается на то же самое
через неделю.

## 9. Учения по восстановлению

Бэкап, который никто не восстанавливал, — не бэкап. На VPS это особенно
верно: диск там чужой и одноразовый.

```bash
make backup-drill
```

Учения поднимают **временные** контейнеры на других портах, вливают в них
последний слепок и сверяют число строк с манифестом. Продовые базы при
этом не трогаются — в скрипте стоят две отдельные защиты от этого.
