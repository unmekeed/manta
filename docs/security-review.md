# Security review (D6)

Дата: 2026-07-25 (обновлено после спринта 58). Объём: монорепо `unmekeed/manta` (254 файла под git,
58 коммитов), развёрнутый dev-стенд. Требования — Гл. 9 спецификации и
NFR-SEC-01/02/03 Гл. 1.

Автоматическая часть воспроизводима: `make security-scan` (в CI — джоба
`security`, валит сборку на критичных находках). Этот документ — ручная
часть: оценка модели угроз, GDPR и принятые риски.

**Ключевой контекст**: платформа развёрнута как одномашинный dev/личный
стенд (WSL2, всё на localhost), публичного доступа нет. JWT/RBAC и
TLS 1.3 реализованы (спринт 58), но на локальном стенде по умолчанию
ВЫКЛЮЧЕНЫ: без `JWT_*`/`TLS_*` ключей gateway слушает HTTP и пускает без
токенов, о чём пишет WARN `auth_disabled`/`tls_disabled`. Включаются
одной командой — `scripts/gen-dev-keys.sh`. Остальное из Гл. 9 (mTLS,
шифрование at-rest, потоки входа) относится к прод-развёртыванию и
помечено ниже как открытое, а не «выполнено».

## 2. Что проверялось автоматически (`scripts/security-scan.sh`)

- **Секреты**: паттерны токена Telegram (`\d{8,10}:AA…`), ключей
  Anthropic, приватных ключей PEM, AWS-секретов, ключа OpenDota — по
  всем отслеживаемым файлам **и по истории коммитов** (`git log -S`).
  Отдельно: `.env`-файлы не должны быть под версионным контролем.
- **Права** на `~/manta-train.env` и `deployments/.env` (ожидается 600).
- **Дефолтные креды**: подсчёт файлов с dev-паролем; при `MANTA_PROD=1`
  находка становится критичной и валит сканер.
- **SCA**: `pip-audit` по каждому `requirements.txt`, `govulncheck` по
  обоим Go-модулям, `npm audit --omit=dev` по фронтенду. Отсутствие
  сканера даёт WARN — «не проверяли» и «чисто» различимы.
- **Поверхность сети**: число проброшенных наружу портов compose.

Осознанно **не** проверяется автоматикой: качество криптографии (своей
нет — только библиотечная) и инъекции в ClickHouse (см. §3).
Бизнес-логика авторизации покрыта юнит-тестами `internal/auth` и
`internal/middleware` (алгоритмическая подмена, истечение, чужой ключ,
отзыв, иерархия ролей, 401/403 на маршрутах).

## 3. Модель угроз (STRIDE, Гл. 9.4) — оценка по факту

| Угроза | Оценка на текущем контуре |
|---|---|
| **S**poofing | JWT RS256 с фиксированным алгоритмом (alg=none и HS256-подмена публичным ключом отвергаются — есть тесты), TTL 15 мин, отзыв по `jti`. Потоки входа (Steam/email) — за сервисом аккаунтов. На стенде без ключей аутентификация выключена осознанно. |
| **T**ampering | Внешние данные (OpenDota JSON, `.dem`) парсятся C++-ядром и Python-коллекторами. Ядро проверяет магию `PBDEMS2` и границы буферов; ошибки парсинга уходят в DLQ, а не роняют конвейер. Kafka-события идут через outbox (at-least-once), витрины — ReplacingMergeTree (повторная доставка идемпотентна). |
| **R**epudiation | Структурные JSON-логи с `trace_id` во всех сервисах; аудит-лога действий пользователя нет (пользователей нет). |
| **I**nformation disclosure | Метрики (9101–9114), ClickHouse (8123), MinIO (9500), Postgres (5432) слушают на всех интерфейсах контейнера и проброшены на хост. В WSL2 это ограничено машиной; **при выносе на публичный хост — закрыть firewall'ом/внутренней сетью**. PII — только публичные никнеймы из OpenDota (§4). |
| **D**enial of service | На gateway — rate limit (`GATEWAY_RATE_LIMIT_RPS`, дефолт 20 rps, burst 40) и RFC 7807-ответ 429. Парсер ограничен размером `.dem` и таймаутом; при сбое — DLQ. Нагрузочный профиль (D5) подтвердил запас: p95 REST 10 мс при 1350 rps с поднятым лимитом. |
| **E**levation of privilege | Роли Гл. 9.3.1 с иерархией уровней и проверкой «не ниже» на каждом закрытом маршруте (тесты на 401/403). Проверки владения ресурсом пока нет — экспорт данных субъекта доступен любой роли premium+ (§4). Сервисы ходят в БД под одной учёткой `dota` с полными правами — для прода нужны раздельные роли (читатель витрин для ml-service/similarity, писатель для extractor/parser). |

**Инъекции в ClickHouse**: запросы формируются двумя способами —
параметризованные (`{match_id:UInt64}` в gateway, report-generator,
extractor) и конкатенацией целочисленных id, приведённых через
`int()`/`%d` (trainers, `dataset-sync`). Строковых пользовательских
данных в SQL нет; `int()` до подстановки исключает инъекцию. Отдельный
риск — `SCALE_TABLE`/имена таблиц в служебных скриптах: они
константы, не пользовательский ввод.

**Цепочка поставки ML** (Гл. 9.5): артефакты моделей лежат в MinIO/MLflow
внутри стенда, промоушен проходит через гейт качества (Brier/AUC) —
подмена модели снаружи невозможна без доступа к стенду. Обучение идёт
на данных OpenDota; отравление датасета теоретически возможно через
подставные матчи, но фильтры (ранг, длительность, патч) и PSI-мониторинг
дрейфа ограничивают эффект.

## 4. GDPR (Гл. 9.7) — что есть и чего нет

**Какие персональные данные фактически хранятся:**

- `PlayerMatchFeatures.player_name` (ClickHouse) — публичный никнейм из
  OpenDota;
- `MatchReports.analysis` (Postgres, jsonb) — те же никнеймы внутри
  отчётов;
- `Players` (Postgres) — таблица схемы Гл. 4.2 со `steam_id_64`,
  фактически 1 тестовая строка;
- `Accounts` (email, password_hash) — **0 строк**: регистрация не
  реализована, паролей в системе нет.

То есть весь объём PII — публичные игровые никнеймы матчей, которые
OpenDota отдаёт открыто; e-mail, паролей, платёжных данных нет.

**Статус требований Гл. 9.7:**

| Требование | Статус |
|---|---|
| Минимизация данных | ✅ по факту: только никнейм и игровая статистика, идентификатор игрока в витрине — слот 0–9, а не аккаунт |
| Хранение / retention | ✅ частично: TTL 14 дней на `ReplayEvents`, `.dem` удаляются после парсинга (`PURGE_PARSED_REPLAYS`) |
| Псевдонимизация | ❌ никнеймы хранятся в открытом виде рядом с аналитикой |
| Право на удаление | ✅ `DELETE /api/v1/players/{id}/data` (роль admin): анонимизация никнейма в ClickHouse (мутация, ответ 202) и в jsonb-отчётах Postgres. Проверено вживую: 7 строк витрины и 11 отчётов → 0 упоминаний, игровая статистика сохранена |
| Право на экспорт | ✅ `GET /api/v1/players/{id}/export` (роль premium): JSON со всеми записями субъекта и списком отчётов |
| Согласие | ❌ неприменимо сейчас (нет пользователей), обязательно при публикации |

**Осталось на публичный релиз (гейт B4):**
1. Псевдонимизация: хранить хэш аккаунта, никнейм — в отдельной таблице
   соответствия, доступной только gateway.
2. Политика retention отчётов (сейчас бессрочно).
3. Привязка аккаунта к никнейму, чтобы работала проверка владения
   (Гл. 9.3.3): сейчас субъект идентифицируется никнеймом, и экспорт
   чужих данных доступен любой роли premium+.

## 5. Принятые риски dev-стенда

Зафиксированы осознанно; при переходе к публичному развёртыванию каждый
становится блокером:

1. **Дефолтные креды** `dota/dota_dev_password` в compose и как fallback
   в коде. Оправдание: стенд не имеет сетевой доступности извне.
   Прод: `POSTGRES_PASSWORD`, `CLICKHOUSE_PASSWORD`, `S3_ACCESS_KEY`/
   `S3_SECRET_KEY` — из секрет-менеджера, сканер с `MANTA_PROD=1`
   валится, если дефолты остались.
2. **Отсутствие TLS** (NFR-SEC-01). Весь трафик — loopback.
   Прод: TLS 1.3 на ingress, mTLS между сервисами.
3. **Отсутствие шифрования at-rest** (NFR-SEC-02). Данные — на диске
   разработчика. Прод: шифрование томов + KMS.
4. **Секреты в plaintext-файле** `~/manta-train.env` (вне git, права
   рекомендованы 600). Прод: Vault/Secrets Manager.
5. **Stdlib-уязвимости Go 1.24.7** (S2) — до обновления тулчейна.

## 6. Рекомендации по приоритету

1. **Обновить Go до 1.25.12+** и пересобрать оба сервиса — закрывает S2
   целиком (одна команда, ломающих изменений в коде не требуется).
2. Перед публикацией: mTLS между сервисами, сертификат от CA, потоки
   входа (Steam OpenID / email+пароль по Гл. 9.2.3 — Argon2id) с
   refresh-ротацией, псевдонимизация PII и проверка владения ресурсом.
3. Раздельные роли БД вместо одной `dota` с полными правами.
4. Держать `make security-scan` в CI зелёным: новые зависимости
   проверяются автоматически, а не раз в фазу.
5. **Включить ключи на локальных стендах**: `scripts/gen-dev-keys.sh` и
   прописать пути в env-файл — иначе gateway работает открыто (это
   логируется как WARN `auth_disabled`/`tls_disabled`).
