# Runbooks инцидентов (D4)

Сценарии — не гипотетические: каждый случился в живом стеке и был
расследован. Формат: симптом → диагностика → причины по частоте → действия.

**Первый шаг любой диагностики — `make doctor`** (спринт 49): проверяет
конвейер по ДАННЫМ (контейнеры, Kafka-топики и консьюмер-группы, свежесть
ReplayEvents/PositionSnapshots/витрины, квота OpenDota, часы WSL vs
контейнеров, применённость миграций) и печатает OK/WARN/FAIL по каждому
пункту. `make recover` сам прогоняет топики+миграции идемпотентно и
заканчивается doctor'ом.

`doctor` отвечает на вопрос «конвейер жив?». На вопрос «почему он
приносит меньше, чем вчера?» отвечает **`make collect-report`** (спринт
86) — диагностический дамп по темпу сбора и покрытию фич; он только
читает и ничего не чинит. Логи сервисов — в `~/manta-logs`
(переопределяется `MANTA_LOG_DIR`; больше НЕ `/tmp`, который гибнет при
рестарте WSL).

## 1. Витрина не растёт

**Симптом.** Telegram-уведомления об обучении прекратились; графика
`training_dataset_matches` — полка; все процессы при этом «up»
(`make recover` показывает OK по всем строкам). Авто-алерт: сообщение
«⚠️ витрина не растёт N ч» (auto-train, `DATASET_STALL_ALERT_H`, по
умолчанию 12 ч) и метрика `training_dataset_stalled=1`.

**Диагностика — одна команда.**

```bash
make collect-report            # весь дамп
make collect-report ARGS=rate  # только темп сбора (быстрее)
```

Она собирает всё, что раньше приходилось выяснять руками, и заканчивается
разделом «как читать»: приток **по источникам** за 24 ч против предыдущих
суток и по часам, курсоры источников, остатки квот OpenDota и STRATZ,
счётчики 429/401/фильтров по каждому логу коллектора, живость процессов
и покрытие каждой фичи. Ниже — те же проверки поштучно, если отчёт
недоступен:

```bash
# 1) когда витрина остановилась
docker exec manta-clickhouse-1 clickhouse-client -q "
SELECT toStartOfHour(computed_at) h, uniqExact(match_id)
FROM manta.MatchTimelineFeatures WHERE computed_at > now()-INTERVAL 36 HOUR
GROUP BY h ORDER BY h"

# 2) квота OpenDota (сброс в 00:00 UTC)
curl -sI https://api.opendota.com/api/health | grep -i remaining

# 3) 429 в логах и метрике
grep -c "429" ~/manta-logs/timeline.log ~/manta-logs/collector.log
curl -s localhost:9108/metrics | grep opendota_rate_limited_total
```

**Прежде чем что-то чинить**, сравните «24ч» с «пред.сутки» по каждому
источнику. Половина суток не даёт половины суточного улова: прайм-тайм
кратно продуктивнее ночи, и «1000 вчера против 190 за полдня» может
означать ровно ноль поломок. Реальная авария выглядит иначе — приток
падает у ОДНОГО источника до нуля и не восстанавливается.

**Причины по частоте.**

1. **Суточный rate limit OpenDota** (реальный случай 2026-07-19: рост шёл
   только 4:00–7:00 — ровно окно от сброса квоты до её исчерпания; тем
   же вечером на другой машине `remaining-day` улетел до **-930** — то
   есть реальный анонимный лимит заметно ниже заявленных ~1660/сутки
   для платного тарифа, burst 60/мин остаётся ориентиром для обеих
   схем). → Дефолты `make recover` бюджетные (до ~1400/сутки: timeline 10
   матчей/30 мин, pro-timeline 5/час, реплей-пути 1/час; отвергнутые
   кандидаты кэшируются, detail-вызовы цикла ограничены
   `TIMELINE_DETAIL_BUDGET`). Считать бюджет через «матчей за цикл»
   НЕЛЬЗЯ: у таймлайна `detail_budget = 2 × limit`, то есть limit 10 —
   это до 20 вызовов за цикл. **С 2026-07-26 темп поднят до ~1780/сутки**
   (`TIMELINE_LIMIT=14`, `PRO_TIMELINE_LIMIT=4`, `OPENDOTA_LIMIT=2` в
   env-файле; раскладка — HANDOFF, «Темп сбора и бюджет квоты») ради
   быстрого набора матчей с сигналами трека F. Это близко к потолку:
   следить за `remaining-day` и при регулярных 429 откатывать
   `TIMELINE_LIMIT` до 12, затем `OPENDOTA_LIMIT` до 1.
   При 429 коллектор сам ждёт до 00:00 UTC + запас вместо обычного
   короткого интервала (не жжёт остаток квоты повторными попытками).
   `OPENDOTA_API_KEY` в `MANTA_TRAIN_ENV` снимает вопрос совсем (код
   поддерживает; сайт opendota.com/api-keys периодически лежит).
1a. **429 при ЦЕЛОЙ суточной квоте** (реальный случай 2026-08-01).
   В логе `429: квота OpenDota исчерпана (remaining-day=2030)` — а
   `curl -sI .../health | grep remaining` показывает почти полный
   остаток. Это не суточный лимит, а burst 60/мин: несколько
   коллекторов сходили в API одновременно. До спринта 85 любой 429
   усыплял коллектор до полуночи UTC, и всплеск на секунды стоил
   14 часов простоя. Теперь при остатке суточной квоты выше
   BURST_DAY_MARGIN сон 90с (`OPENDOTA_BURST_SLEEP_S`). Если 429
   повторяются часто — разнести интервалы коллекторов, чтобы циклы не
   стартовали одновременно.
2. **Умер процесс конвейера** (перезапуск среды убил dockerd и фоны;
   реальные случаи 2026-07-16/18/19). → `make recover` — идемпотентен.
   Подслучай (2026-07-20): рестарт Docker Desktop пересоздал
   Postgres/Kafka, а процессы коллекторов остались живы со СТАРЫМИ
   соединениями — `pgrep` их видит, recover пропускает, но каждый цикл
   падает `psycopg.OperationalError: server closed the connection`.
   Начиная со спринта 47 коллекторы переподключаются к PG сами
   (лог «postgres: соединение умерло — переподключаюсь»); на старом
   коде — `pkill -f "collector --source"` и `make recover`.
3. **ClickHouse после нечистого рестарта** долго разгребает temp-мерджи
   или упёрся в file-descriptor limit (реальный случай 2026-07-19:
   `Too many open files` в logs → зацикленный мердж `system.metric_log`).
   → дождаться Ready for connections; при зацикленном мердже —
   `docker restart manta-clickhouse-1` в тихое окно.
4. **Код обновился, миграция — нет** (реальный случай: similarity падал
   404 на `networth_total`, отсутствующей в схеме). → `make migrate-ch`.
4a. **Вышел новый патч Dota** (реальный случай 2026-07-31, 7.41). Приток
   падает почти до нуля при полностью зелёном `make doctor`: фильтр
   принимал только матчи текущего патча, а в первые сутки их почти нет.
   С спринта 81 граница — `latest − PATCH_LAG` (дефолт 1, то есть
   текущий и предыдущий), но если приток всё же встал сразу после
   патча — поднять `PATCH_LAG=2` в env-файле и перезапустить. В логе
   коллектора видно строку `актуальный патч: id=N, принимаю от id=M`.
4b. **Valve сменили формат сжатия реплеев** (реальный случай 2026-07-31:
   bz2 → zstd вместе с патчем 7.41, расширение в URL осталось
   `.dem.bz2`). Симптом: реплейный путь стоит с `processed=0`, в логе
   `неизвестный формат сжатия (первые байты b'...')`. Формат
   определяется по магии, а не по имени файла, поэтому лечение — добавить
   ветку в `decompress()` (`sources/opendota.py`). Известные сигнатуры:
   `BZh` — bz2, `28 b5 2f fd` — zstd, `PBDEMS2` — уже распакован.
   Первые байты из сообщения дают ответ за минуту: сравнить их со
   списком магических чисел форматов сжатия.
5. **STRATZ-коллекторы молчат** (спринт 79). Смотреть
   `~/manta-logs/stratz.log` и `stratz-pro.log`:
   - `401`/`403` — токен недействителен или отозван; проверить
     `STRATZ_API_TOKEN` в env-файле. Демон не падает, но и не собирает.
   - `429` — исчерпан почасовой (2000) или суточный (10000) лимит;
     коллектор сам ждёт час (`STRATZ_RATE_SLEEP_S`). Регулярные 429 —
     снижать `STRATZ_LIMIT`.
   - `STRATZ GraphQL: ... — обрываю цикл` — схема STRATZ разошлась с
     запросом; в тексте ошибки названо конкретное поле, править
     `MATCH_FIELDS` в `collector/sources/stratz.py`.
   - в логе `выставить STRATZ_KILLS_CUMULATIVE=1` — ряд убийств приходит
     уже накопительным, и он накапливается второй раз; выставить
     переменную и перезапустить, иначе `kills_*` в датасете завышены.
   Проверить вклад источника в витрину:
   ```sql
   SELECT feature_version, count(DISTINCT match_id)
   FROM MatchTimelineFeatures GROUP BY feature_version;
   ```

### 1.1 В логе 5xx или обрыв связи — лежит чужой сервер

```
HTTPError: 522 Server Error for url: https://api.opendota.com/api/constants/patch
WARNING 522 от opendota-public — сбой на их стороне, не квота; повтор
        через 300s вместо обычных 3600s (обрывов подряд: 1)
```

**Сначала убедиться, что лежит не машина** — запросом С ДРУГОЙ сети (с
телефона, из другого места), а не с самой VPS:

```bash
curl -sS -o /dev/null -w "%{http_code}\n" --max-time 25 \
     https://api.opendota.com/api/constants/patch
```

`522` и оттуда — Cloudflare не достучался до origin OpenDota; чинить
нечего, ждать. `200` оттуда при `522` у нас — беда сетевая, смотреть на
машину.

Чинить обычно не нужно: со спринта 146 коллектор различает «нас
ограничили по квоте» и «у них упал сервер». Первое ждёт до сброса, второе
повторяется через 5 минут с удвоением (`TRANSIENT_SLEEP_S`), возвращаясь
к обычному интервалу за четыре обрыва подряд; успешный цикл счётчик
обнуляет. До спринта 146 обе беды попадали в одну ветку, и
двадцатисекундная неполадка у Cloudflare стоила часа сбора.

Тревожно, если «обрывов подряд» растёт сутками: тогда сбой не чужой, а
наш — смотреть DNS, исходящий фаервол, прокси.

### 1.2 Реплеи не разбираются: PositionSnapshots пуст

**Симптом.** Матчи в витрине есть, а карт нет ни одной:

```bash
docker exec manta-clickhouse-1 sh -c 'clickhouse-client \
  --user "$CLICKHOUSE_USER" --password "$CLICKHOUSE_PASSWORD" -q "
SELECT (SELECT uniqExact(match_id) FROM manta.MatchTimelineFeatures) AS matches,
       (SELECT count() FROM manta.PositionSnapshots)                 AS positions,
       (SELECT count() FROM manta.MatchMapCellsMinute)               AS cells"'
```

`matches` растёт, `positions` — ноль. Значит работает только JSON-путь, а
реплейный стоит. Карты строятся ТОЛЬКО из реплеев, поэтому выглядит это
как «сломались карты».

**Смотреть логи качающего, а не разбирающего:**

```bash
docker logs --tail 30 manta-pro-replay-collector-1
```

`ConnectTimeoutError` на `replay*.dota2.com.cn` — реплеи раздаёт
региональный CDN Valve, и китайский кластер доступен не отовсюду. С
машины в Европе он обычно недостижим; проверить прямо:

```bash
curl -sS -o /dev/null -w "%{http_code} %{time_connect}s\n" --max-time 15 \
     http://replay413.dota2.com.cn/
```

Чинить тут нечего — маршрута нет. Важно другое: со спринта 150 такое
соединение отваливается за 10 секунд, а не за 600, и коллектор идёт к
следующему матчу вместо того, чтобы стоять на недостижимом почти час.
До спринта 150 очередь не двигалась вовсе.

Если недостижимых матчей много подряд, реплейный путь наполняется
медленно — это не поломка, а география. Ускорить можно только своим
источником матчей (Steam GC), где кластер выбирается не за нас.

### 1.3 Реплеи не берутся: недостижимый кластер Valve

Реплеи раздаёт региональный CDN, и кластер выбирает Valve, а не мы. Во
время The International 2026 почти весь про-поток шёл с китайского
кластера (`replay413.dota2.com.cn`), недостижимого и с VPS в Ирландии, и
с домашней машины.

Такие матчи **паркуются**, а не теряются (спринт 153). Курсор уходит
вперёд — очередь важнее одного матча, — но запись остаётся:

```bash
make replay-parked        # по каким хостам стоит очередь
```

Хост, дважды не ответивший подряд, перестаёт опрашиваться на шесть часов
(`UNREACHABLE_TTL_S`): матчи с него паркуются без единой попытки. Без
этого один матч стоил бы восьмидесяти секунд — DNS отдаёт несколько
адресов, и каждый пробуется по таймауту соединения.

Когда маршрут появился — прокси, другая машина, конец турнира:

```bash
make replay-retry         # вручную; в расписание НЕ ставится
```

В расписании его нет намеренно: пока маршрута нет, повтор сожжёт бюджет
вызовов на те же таймауты, а у реплейного источника его 50 в сутки.

### 1.4 Своя разбивка стоит: очередь кандидатов пуста

**Симптом.** `candidates-collector` работает, в логе каждые пять минут
«цикл кандидатов: взято 0, отдано 0», реплеи не идут. Со спринта 154 он
сам называет причину — но она бывает не последней в цепочке.

Цепочка такая: `seed` проходит по потоку Valve и запоминает аккаунты,
`fill` разрешает их ранги, `scan` отбирает матчи в очередь. Пустая
очередь означает, что оборвалось одно из трёх звеньев.

```bash
docker exec manta-candidates-collector-1 python -m collector.ranks seed
docker exec manta-candidates-collector-1 python -m collector.ranks fill
docker exec manta-candidates-collector-1 python -m collector.ranks scan
```

**`fill: HTTP 403: STRATZ не принимает токен`** — токен протух или
отозван. `fill` по умолчанию берёт STRATZ, если токен ЗАДАН, — а задан и
действителен не одно и то же. Проверить: `python -m collector.ranks
probe`. Обойти, не дожидаясь нового токена:

```bash
docker exec manta-candidates-collector-1 \
    python -m collector.ranks fill --resolver opendota
```

OpenDota тратит запрос НА ИГРОКА и делит свои ~2000 в сутки с
коллекторами, поэтому автоматически на него никто не переключается: это
решение про чужую квоту, и принимают его руками.

До спринта 155 такой прогон молча делал сорок запросов подряд, получал
сорок раз 403 и заканчивался нулём рангов. Теперь он обрывается на
первом отказе и говорит, что делать.

**Воронка `scan` показывает «мало известных рангов»** — это не поломка, а
пустой кэш: пока `fill` не разрешил ранги, отбирать не по чему. 65%
профилей Steam скрыты, так что видимых игроков около 3.5 из 10 — кэш
наполняется медленно и по большей части из повторных встреч.

## 2. Гейт всё отклоняет

**Симптом.** Подряд ≥5 «⏸ отклонена гейтом» в Telegram; в реестре версии
копятся, production не двигается.

**Диагностика.** Смотреть текст причины в уведомлении: гейт печатает
`new X vs prod Y (Δ, σ)` и режим сравнения (fresh-holdout / про-эталон).

**Причины.**

1. **Это норма, а не инцидент**, если Δ в пределах ±2σ и знак скачет:
   датасет вырос на малую долю, реальной разницы нет — гейт честно
   отказывает «не лучше». Вмешательство не нужно; продвижение случится
   на осмысленном приросте данных.
2. **Prod «удачно» стоит на старом эталоне** (случай спринта 27, из-за
   которого гейт и переписан): сравнение шло на разных данных.
   Проверить, что обе модели оцениваются на одном holdout
   (лог `evaluate_gate`: «одни данные (N матчей)»).
3. **Систематически хуже после смены фич** — новая фича добавила NaN-строк
   (JSON-путь не даёт позиций). Проверить долю NaN в
   `training.dataset` и веса строк (спринт 33).

## 3. PSI-алярм (дрейф фич)

**Симптом.** `wp_psi_max` > 0.2, уведомление «⚠️ дрейф фич»; авто-обучение
запускается по триггеру drift чаще обычного.

**Причины.**

1. **Баланс-патч Dota** — ожидаемое поведение контура CT (Гл. 10.4,
   R-02): мета сменилась, PSI-триггер для того и заведён. Ничего не
   делать; следить, что гейт пропустил модель на новых данных. При
   большом патче рассмотреть даунвейт старых матчей (A9 роадмапа).
2. **Сломался источник данных**, а не мета: например, коллектор начал
   писать нули/NaN в одну фичу (обрыв позиций → `position_advance`).
   Отличие от патча: дрейфит одна фича, а не спектр; смотреть
   `wp_feature_psi{feature=...}` по отдельности.
3. **Перенаполнение витрины** после сброса/ремиграции — распределение
   то же, но состав матчей другой. Разовый алярм, самоуспокоится.

## 4. Реплейный путь стоит (витрина при этом растёт)

**Симптом.** Уведомление «⚠️ реплейный путь стоит» (auto-train,
`REPLAY_STALL_ALERT_H`, по умолчанию 6 ч), метрика
`training_replay_path_stalled=1`. Витрина может продолжать расти —
JSON-путь маскирует проблему, поэтому у реплейного пути отдельный алерт.

**Диагностика.** `make doctor` — покажет отсутствующие топики, мёртвые
консьюмер-группы и свежесть `ReplayEvents` одним прогоном.

**Причины по частоте.**

1. **Потерянные Kafka-топики** (volume пересоздался; автосоздание
   выключено): продюсер теряет сообщения МОЛЧА. С спринта 49 recover
   сам прогоняет `make topics`, но если стек не перезапускали —
   `make topics` + перезапуск parser-svc и feature-extractor.
2. **Упавший parser-svc / extractor** — смотреть `~/manta-logs/`.
3. **Квота OpenDota** — реплейные коллекторы уснули до 00:00 UTC
   (это нормально; см. runbook 1).
4. **Курсор реплейного источника встал** (до спринта 78 — вечно).
   Отличительный признак: лаг группы `replay-parser` РАВЕН НУЛЮ, и
   `grep -c "collected match_id" ~/manta-logs/pro-collector.log` = 0.
   Значит парсеру просто нечего разбирать — обрыв на стороне сбора, а
   зелёный лаг здесь ничего не доказывает. В логе коллектора при этом
   каждый цикл одно и то же: `Invalid data stream` или `skip duplicate`
   на одном и том же `match_id`. С спринта 78 коллектор разбирает такой
   затор сам (курсор сдвигается через несобираемый матч), но разгребает
   по `OPENDOTA_LIMIT` матчей за цикл. Если отставание большое и ждать
   нет смысла, курсор перематывают вручную:

   ```sql
   -- посмотреть, где стоит и насколько отстал
   SELECT source_name, cursor_value, updated_at FROM CollectorCursor;
   -- перемотать на свежую позицию (пропускает старые про-матчи —
   -- они почти все уже собраны timeline-источником)
   UPDATE CollectorCursor SET cursor_value = '<свежий match_id>',
          updated_at = NOW() WHERE source_name = 'opendota';
   ```

## 5. Обновление кода на локалке (после git pull)

**Ловушка.** `make recover` запускает сервис, только если тот ещё не жив
(`if ! pgrep`). Поэтому сам по себе он НЕ перезапускает уже работающие
процессы — после `git pull` они продолжают крутить старый код. Симптом
самый неприятный из возможных: doctor зелёный, всё «up», а новая
функциональность не работает, потому что в памяти прежняя версия.

**Штатный порядок:**

```bash
cd ~/manta
make stop                 # только хостовые процессы; контейнеры и данные целы
git pull origin main
make migrate              # новые миграции PG + CH (журнал не даст прогнать дважды)
make recover              # поднимает всё заново уже на новом коде
make doctor               # вердикт по данным
```

`make stop` (scripts/dev-stop.sh) шлёт SIGTERM и ждёт до 10 с на процесс,
прежде чем добить -9: обрыв на середине INSERT в ClickHouse или до
коммита оффсета Kafka — это потерянные данные, а не «просто рестарт».

**Модель останавливать отдельно не нужно.** Артефакт несёт свой набор
фич (`predictors.WinProbability.features`), а сервер собирает вектор по
именам из него же — поэтому и старая, и новая версия модели корректно
работают с обновлённым кодом. Обратное неверно: читатель, который шлёт
МЕНЬШЕ фич, чем ждёт модель, получает INVALID_ARGUMENT «missing
features» — так чуть не встали отчёты при расширении FEATURES с 10 до 22
в треке F. Наборы фич report-generator и ml-service сторожит тест
`report-generator/tests/test_wp_features_sync.py`.

---

Общий принцип: сначала `make doctor` (быстрый вердикт по данным), затем
`make recover` (безопасен на живом стеке; сам чинит топики/миграции),
потом диагностика по метрикам (`scripts/dashboard.py` — живой дашборд без
Grafana), и только затем ручные вмешательства в контейнеры/данные.
