# Трек F — максимальное усиление Win Probability

Дата анализа: 2026-07-26 (после спринта 58). Цель: модель, сильная на
КАЖДОЙ фазе игры и учитывающая максимум переменных — от драфта до
предметов и нейтралок. План основан на аудите фактических источников
данных, а не на списке пожеланий.

---

## 1. Отправная точка (честная)

Текущая WP v0.7 — 10 фич, все командно-разностные:
`game_time, networth_diff, xp_diff, kills_diff, kills_total,
position_advance, alive_diff, towers_diff, rax_diff, networth_rel`.

Фазовые Brier последнего обучения (519 матчей, вторая локалка):
early **0.186** / mid 0.077 / late 0.096. База (константа 0.5) — 0.25.

**Диагноз**: в mid/late модель уже близка к потолку одиночных разностных
фич (исход в основном определён экономикой). Вся зона роста — ранняя
игра: до 10-й минуты золото ещё ровное, и модель почти слепа. Ранняя
игра решается не «ещё одной разностью», а информацией, которая известна
ДО того, как экономика разошлась: драфт, лайнинг-матчапы, первые
покупки, контроль рун и карт.

## 2. Аудит источников: что у нас уже есть и что мы выбрасываем

### 2.1. JSON распаршенного матча OpenDota (гибридный путь, ~90% датасета)

Коллектор `opendota-timeline` скачивает ПОЛНЫЙ JSON матча (один вызов
/matches/{id}), но `timeline_rows()` извлекает только: `radiant_gold_adv`,
`radiant_xp_adv`, `kills_log`, `objectives(building_kill)`, `radiant_win`,
`patch`. **Всё остальное выбрасывается**, хотя уже оплачено квотой:

| Поле JSON | Сигнал | Фаза влияния |
|---|---|---|
| `picks_bans[]` | полный драфт: 5+5 героев, баны, порядок | вся игра, критично для early |
| `players[].hero_id` | составы (даже без picks_bans) | вся игра |
| `players[].purchase_log[]` | тайминг КАЖДОЙ покупки каждого игрока | early/mid (тайминги ключевых предметов) |
| `players[].item_0..5, backpack, item_neutral` | финальный инвентарь + нейтралка | признаки для пер-игрокового анализа |
| `players[].obs_log[], sen_log[]` | установка вардов с координатами и временем | вижн-контроль по минутам |
| `players[].runes_log[]` | подбор рун (тип, время) | early (bounty/water/power runes) |
| `players[].buyback_log[]` | бэйбеки с временем | late (решающие тимфайты) |
| `objectives`: `CHAT_MESSAGE_ROSHAN_KILL` | убийства Рошана (+ team) | mid/late |
| `objectives`: `CHAT_MESSAGE_AEGIS`, `AEGIS_STOLEN`, `DENIED_AEGIS` | судьба аегиса | mid/late |
| `objectives`: `CHAT_MESSAGE_FIRSTBLOOD` | first blood (время, слот) | early |
| `objectives`: `CHAT_MESSAGE_COURIER_LOST` | убийства курьеров | early |
| `teamfights[]` | тимфайты: старт/конец, урон, смерти по игрокам | mid |
| `players[].gold_reasons, xp_reasons` | структура дохода (крипы vs герои vs здания) | mid |
| `players[].lane, lane_role, is_roaming` | роли (наша lane-детекция есть только у реплейных) | early |
| `players[].item_uses` | использования (смоки, дасты, глифы — агрегат) | вижн/ганги |
| `draft_timings[]` | время раздумий на пиках | слабый сигнал, скорее продукт |

**Вывод**: крупнейший клад лежит в уже скачиваемых данных. Ноль новых
API-вызовов, ноль квоты.

### 2.2. Реплейный путь (C++ ядро)

Combat log ядро УЖЕ парсит типы: DAMAGE, HEAL, MODIFIER_ADD/REMOVE,
DEATH, ABILITY, ITEM, LOCATION, **GOLD, XP, PURCHASE, BUYBACK**,
GAME_STATE — но в ClickHouse пишутся только 6 типов
(DAMAGE/HEAL/KILL/ABILITY_CAST/ITEM_PURCHASE/WARD_PLACE). BUYBACK/GOLD/XP
отбрасываются на записи. Сущности: NetWorth, TotalEarnedGold/XP,
LastHitCount, позиции, is_alive. Не извлекаются (но есть в реплее):
уровень героя, инвентарь по времени, стаки модификаторов (аегис, смоки),
состояние Рошана.

### 2.3. Чего нет нигде (и не будет без больших затрат)

Кулдауны ультимейтов, точный вижн-скор врага, скрытая информация
(предметы в тумане). Не планируем — соотношение усилий и профита плохое.

## 3. Архитектурное решение №0: перестать выбрасывать данные

Каждая новая фича сейчас требует пересбора с нуля, потому что сырой JSON
не сохраняется. Поэтому первым делом:

- **Складывать сжатый исходный JSON каждого матча в MinIO**
  (`s3://matches-json/{match_id}.json.gz`, ~50–150 КиБ на матч, gzip).
  Тогда ЛЮБАЯ будущая фича бэкфиллится по всей истории без единого
  API-вызова. Это страховка от главного дефицита проекта — квоты.
- Двойная запись с первого дня: сырой JSON + извлечённые фичи.

## 4. Целевая архитектура модели

Одна плоская модель не выражает «драфт задаёт прайор, экономика его
уточняет». Целевая схема — **двухкаскадная**:

```
Draft Prior Model  P(win | составы, патч)      — обучается на пер-матчевых
        │                                        данных (1 строка = матч)
        ▼  выход как фича
WP Timeline Model  P(win | t, экономика, объективы, вижн, draft_prior)
```

- В минуту 0 WP = draft prior (осмысленный старт вместо 0.5).
- По мере игры вес прайора естественно падает (LightGBM сам выучит).
- Прайор-модель полезна и сама по себе: это Draft Predictor спеки
  (Гл. 6.2.1) и апгрейд Draft Engine (:50053).

Представление героев для прайора (по мере роста датасета):
1. **Сейчас (≈5К матчей)**: агрегатные фичи — средний винрейт героев
   состава в текущем патче (по СОБСТВЕННОЙ витрине), суммарные
   атрибуты состава из констант (мили/рейндж, физ/маг урон, точки силы
   по фазам out of hero stats), синергия/контра из частот Draft Engine.
2. **Позже (20К+)**: обучаемые эмбеддинги героев (факторизация
   матрицы «состав → исход») или GNN по графу синергий из спеки.

## 5. Каталог новых фич по спринтам

### F1 (спринт 60) — фундамент данных: ничего не выбрасывать
Профит: разблокирует всё остальное; сам по себе +0 к метрике.
1. MinIO-бакет `matches-json`; timeline-коллекторы пишут gzip-JSON до
   извлечения фич. Реплейный путь — folder `opendota/{id}.json` detail.
2. Новая пер-матчевая таблица CH **MatchDraft**: match_id, patch,
   radiant_heroes[5], dire_heroes[5], bans[], first_pick_team, tier.
3. Новая таблица **MatchEvents** (пер-матчевые события общего вида):
   match_id, time, kind(roshan|aegis|aegis_stolen|firstblood|courier|
   buyback|rune|ward_obs|ward_sen|smoke), team, extra JSON. Пишется из
   уже скачанного JSON. Бэкфилл-скрипт по сохранённым JSON.
4. Запись BUYBACK из C++ ядра в ReplayEvents (тип уже парсится).

### F2 (спринт 61) — объективы в WP: Рошан, аегис, бэйбеки, first blood
Профит: заметный в mid/late; закрывает половину A10.
Новые поминутные фичи витрины (все — из MatchEvents, NaN для старых строк):
- `roshan_diff` — убийства Рошана R−D накопительно;
- `aegis_alive` — у какой стороны сейчас аегис (−1/0/+1);
- `buybacks_used_diff` — потрачено бэйбеков R−D (окно 5 мин);
- `first_blood` — сторона FB (константа с момента события).
Переобучение WP → v0.8, фазовый контроль (ожидание: улучшение mid/late).

### F3 (спринт 62) — Draft Prior v1 + каскад
Профит: ГЛАВНЫЙ удар по early (0.186 → цель ≤0.15).
1. Тренер `training/draft_prior.py`: LightGBM на пер-матчевых строках
   MatchDraft; фичи-агрегаты составов (п.4.1); GroupSplit по патчу не
   нужен — 1 строка = 1 матч; калибровка; реестр `draft_prior`.
2. Витрина: колонка `draft_prior` (заполняется extractor'ом/бэкфиллом
   через инференс прайор-модели).
3. WP v0.9 с фичей draft_prior; отдельный фазовый отчёт до/после.
4. Draft Engine начинает отдавать прайор вместо чистых частот.

### F4 (спринт 63) — предметы: тайминги силы закупа
Профит: mid; интерпретируемость отчётов (тайминги — язык игроков).
Из `purchase_log` (JSON) / PURCHASE (реплей):
- словарь стоимостей предметов (константы OpenDota, локальный файл);
- `item_value_diff` — суммарная стоимость закупа R−D к минуте t
  (прокси net worth в предметах, ловит «сидит на деньгах»);
- `key_items_diff` — счёт «ключевых таймингов» (blink, bkb, mek,
  pipe, aghs, refresher: список фиксированный) R−D к минуте t;
- пер-игроково для отчётов: тайминг ключевого предмета vs медиана
  своего героя по датасету («блинк на 22-й — поздно на 4 мин»).

### F5 (спринт 64) — вижн и руны
Профит: early/mid; уникальные фичи, которых нет у простых моделей.
- `obs_wards_diff` — активные обс-варды R−D в минуту t (из obs_log,
  время жизни 6 мин или до снятия — в JSON есть время снятия);
- `sentries_placed_diff`, `wards_killed_diff`;
- `runes_diff` — подобранные power-руны R−D накопительно; bounty
  отдельно в early (`bounty_runes_diff` до 10-й минуты);
- `smokes_used_diff` (из item_uses/purchase_log — приближение).

### F6 (спринт 65) — нейтральные предметы и уровни
- `neutral_tier_sum_diff` — сумма тиров нейтралок состава R−D
  (из item_neutral финального + времена тиров констант — приближение;
  из реплея точно, если расширить ядро на инвентарь);
- `levels_sum_diff`, `max_level_diff` — из XP-таймлайна (реплей:
  добавить m_iCurrentLevel в entities; JSON: xp_adv уже есть, уровни
  восстановимы по таблице опыта — дешёвое приближение).

### F7 (спринт 66) — Optuna и стэкинг (вторая половина A10)
Когда фич станет 25+, ручные гиперпараметры перестанут быть адекватными:
- Optuna: поиск по num_leaves/min_data/lambda/lr на OOF-Brier,
  бюджет ~200 траялов, отдельно для WP и draft_prior;
- монотонные ограничения пересмотреть для новых фич (roshan_diff — 
  монотонная, wards — нет);
- попробовать пер-фазные модели (early/mid/late отдельными бустерами,
  общий калибратор) против единой — принять по фазовым Brier.

### F8 (спринт 67) — hero-эмбеддинги (гейт: 20К+ матчей)
Факторизация «составы → исход» (ALS/логистическая с эмбеддингами
размерности 8–16), эмбеддинги героев как фичи прайора; синергия/контра
пар из скалярных произведений. GNN спеки — после и только если
эмбеддинги упрутся.

## 6. Правила, которые не меняются

- Каждая фича — через миграцию с DEFAULT NaN/0: старые строки честно
  «не знают», LightGBM обрабатывает пропуск нативно.
- Каждый спринт: переобучение, фазовые Brier до/после, честный гейт,
  ROADMAP+HANDOFF. Фича, не двинувшая метрику на живом датасете, —
  выкидывается (прецедент уже был в спринте 25).
- Разбиение по матчам, зеркалирование сторон, даунвейт старого патча —
  без изменений.
- Квота — по-прежнему бутылочное горлышко: НИ ОДИН спринт трека F не
  добавляет API-вызовов. Всё — из уже скачиваемого/сохранённого.
