# Гайд по модели Win Probability

Практическое руководство: что модель делает, куда смотреть, что означает
каждое число и как отличить работающую модель от сломанной.

Состояние на 2026-07-31: production `0.8.0-20260731T071333Z`,
Brier на про-эталоне **0.1682** при целевом пороге ≤ 0.18.

---

## 1. Что модель предсказывает

Одно число: **вероятность победы команды Radiant** в конкретный момент
матча. Не «кто сильнее», не «кто ведёт по золоту», а именно вероятность
итоговой победы при том состоянии игры, которое сложилось на эту минуту.

Вход — состояние матча на минуте N. Выход — число от 0 до 1.

- `0.50` — модель не знает, кто победит (равная игра или слишком рано);
- `0.75` — Radiant побеждает примерно в 3 случаях из 4 при таком раскладе;
- `0.02` — Radiant почти наверняка проиграл.

Ключевое свойство — **калиброванность**. Если взять все моменты, где
модель сказала 0.70, то Radiant должен выиграть примерно в 70% из них.
Модель, которая всегда права в направлении, но говорит 0.99 там, где
реально 0.70, считается плохой: её числами нельзя пользоваться как
вероятностями.

Модель предсказывает **на каждую минуту отдельно**, независимо. Она не
видит будущего и не помнит прошлого — только срез текущей минуты.
Поэтому WP-кривая может дёргаться: это не ошибка, а следствие того, что
каждая точка считается заново.

## 2. Откуда берутся данные

```
источники (OpenDota JSON / STRATZ GraphQL / реплеи .dem)
        ↓
   ClickHouse: MatchTimelineFeatures — по строке на минуту матча
        ↓
   training/dataset.py — сборка X (фичи), y (исход), groups (match_id)
        ↓
   training/train_winprob.py — LightGBM + калибровка
        ↓
   реестр моделей (MinIO/MLflow) → стейдж production
        ↓
   ml-service (gRPC :50051) → API → фронтенд
```

Одна строка витрины = одна минута одного матча. Матч на 40 минут даёт
40 строк, и у всех них **одинаковый** `radiant_win` — целевая метка это
итог матча, известный задним числом.

Три источника дают разную полноту:

| источник | `feature_version` | что даёт | чего нет |
|---|---|---|---|
| OpenDota JSON | `opendota-json@3` | ядро + весь трек F | позиции (только в реплее) |
| STRATZ GraphQL | `stratz-graphql@1` | ядро | позиции и трек F |
| реплеи `.dem` | `1.4.0` | всё, включая позиции | — |

Отсутствующие фичи пишутся как **NaN**, а не ноль. Это принципиально:
LightGBM обрабатывает пропуск нативно (отправляет в отдельную ветку
дерева), а ноль был бы ложным сигналом. Для `position_advance` ноль
означал бы «бой ровно в центре карты» — совсем не то же самое, что
«позиций нет».

Посмотреть состав датасета:

```bash
docker exec manta-clickhouse-1 clickhouse-client -q "
SELECT feature_version, count(DISTINCT match_id) AS matches, count() AS rows
FROM manta.MatchTimelineFeatures GROUP BY feature_version ORDER BY rows DESC"
```

## 3. Фичи: что означает каждая

Все `*_diff` — это **разность Radiant минус Dire**. Положительное
значение в пользу Radiant, отрицательное — в пользу Dire.

**Ядро**

| фича | смысл |
|---|---|
| `game_time` | секунды с начала матча. Модель должна знать фазу: 5к золота на 10-й минуте и на 40-й значат разное |
| `networth_diff` | разница суммарного нетворса команд |
| `networth_rel` | `networth_diff / networth_total` — доля преимущества. 5к разницы при 20к общего золота это разгром, при 100к — почти ничего |
| `xp_diff` | разница суммарного опыта |
| `kills_diff` | разница убийств накопительно |
| `kills_total` | всего убийств в матче — прокси «насколько игра драчливая» |
| `levels_diff` | сумма уровней героев |

**Карта и объекты**

| фича | смысл |
|---|---|
| `towers_diff` | снесённые башни, накопительно |
| `rax_diff` | снесённые бараки. Самый весомый объект: потеря казарм часто необратима |
| `position_advance` | территориальное продвижение от −1 до +1: где происходит игра. +1 — бои у трона Dire |
| `alive_diff` | сколько героев живо прямо сейчас **по всей карте**. Мощный сигнал: 5 против 2 означает, что сейчас снесут объект |
| `local_manpower_diff` | перевес **в точке боя**: сколько героев каждой стороны рядом со стычкой. Закрывает слепое пятно `alive_diff` — «пятеро против пятерых, но трое на другом краю карты» |
| `spread_diff` | собранность: разброс героев относительно центра масс команды. Отрицательное — Radiant идёт кучей |
| `roshan_diff` | убийства Рошана |
| `aegis_alive` | у кого сейчас аегис: −1 / 0 / +1 |

**Экономика и предметы**

| фича | смысл |
|---|---|
| `item_value_diff` | разница стоимости закупа |
| `key_items_diff` | ключевые предметы (BKB, Blink и подобные) — не всё золото одинаково полезно |
| `neutral_tier_diff` | сумма тиров нейтральных предметов |
| `buybacks_diff` | **потрачено** бэйбеков. Потраченный бэйбек — минус ресурс на следующий замес |
| `buyback_availability` | сколько героев **могут** выкупиться прямо сейчас (не на кулдауне и золота хватает), от −5 до +5. Обратная сторона предыдущей: та считает израсходованный резерв, эта — оставшийся |
| `unspent_gold_diff` | золото в кармане, не вложенное в предметы. Мёртвый ресурс — но и запас под бэйбек, поэтому знак вклада решает модель |

**Прочее**

| фича | смысл |
|---|---|
| `first_blood` | какая сторона взяла первую кровь |
| `obs_wards_diff` | активные обзорные варды — контроль информации, **штуками** |
| `vision_coverage_diff` | **доля карты** под обзором, от −1 до +1. Отличается от счётчика тем, что видит перекрытие: три варда в одном лесу дают меньше площади, чем три разнесённых |
| `sen_wards_diff` | поставленные сентри |
| `runes_diff` | подобранные руны |

> `draft_prior` из модели **удалён** в спринте 134: при 3420 матчах
> Δ = +0.00001 ± 0.00008, то есть плоско до пятого знака при пороге
> значимости 0.001. Сама Draft Prior Model осталась — у неё свой продукт
> (DraftService), к Win Probability она отношения больше не имеет.

### Чем фичи защищены от тихой порчи

Поведение фичи («знак в пользу Radiant», «вард живёт шесть минут»)
проверяют около сорока обычных тестов. Но свойства переживают правку
арифметики: подели стоимость выкупа на 12 вместо 13 — каждое свойство
останется верным, а числа модели поедут.

Поэтому числа закреплены отдельно, тремя эталонами (спринт 137):

```bash
make golden-test              # проверить: без БД и сети, секунды
make signals-golden-update    # ПЕРЕПИСАТЬ эталон — осознанное решение
```

| эталон | что закрепляет |
|---|---|
| `apps/data-collector/tests/fixtures/golden_features.json` | 14 поминутных фич из JSON матча, 13 минут |
| `apps/ml-service/tests/fixtures/golden_rates.json` | 15 производных на 6 сценариях |
| `apps/ml-service/tests/fixtures/golden_vector.json` | все 41 фича **в порядке FEATURES**, 8 сценариев |

Третий важнее двух первых: он единственный проверяет ПОРЯДОК.
Перестановка двух колонок ничего не ломает заметно — модель просто молча
учится на перепутанных признаках, и именно это уже стоило нескольких
суток простоя (спринты 90–91).

**Если `make golden-test` упал — это не устаревший эталон, это регресс.**
Обновлять эталон можно, только когда формулу изменили осознанно, и тогда
каждое изменившееся число обязано быть объяснено в сообщении коммита.
Флага «обновить из-под pytest» нет намеренно: он превратил бы регресс в
самоподтверждающийся — любая правка молча переписывала бы эталон под
себя.

## 4. Как модель обучается

**LightGBM** — градиентный бустинг на деревьях. Выбран потому, что
нативно ест NaN и хорошо работает на табличных данных небольшого объёма.

Четыре механизма, которые важно понимать, потому что они объясняют
странности в метриках:

**Зеркалирование (mirror).** Каждая обучающая строка дублируется с
переменой сторон: все `*_diff` меняют знак, `draft_prior` переходит в
`1 − p`, метка инвертируется. Это делает модель **симметричной**: она не
имеет мнения о том, что «Radiant побеждает чаще». Без этого модель
впитала бы перекос выборки (в пабликах Radiant выигрывает около 57%) и
переносила бы его на про-матчи, где счёт близок к 50/50.

**Группировка по матчам.** Валидация делится по `match_id` целиком, а не
по строкам. Если бы минуты одного матча попали и в обучение, и в
валидацию, модель «подсмотрела» бы исход — метрика получилась бы
фиктивно хорошей.

**OOF-калибровка.** Сырой выход бустинга — не вероятность. Его калибрует
изотоническая регрессия (или Platt при менее чем 50 матчах), обученная на
out-of-fold предсказаниях пятифолдовой кросс-валидации. С 2026-07-31
калибратор учится и на зеркальных парах, поэтому он тоже симметричен:
`cal(p) + cal(1−p) ≈ 1`.

**Даунвейт старых патчей (A9).** После баланс-патча мета меняется, но
выбрасывать старые матчи расточительно. Вместо этого их вес умножается на
`PATCH_OLD_WEIGHT^(возраст в патчах)`, по умолчанию 0.4 за патч, не ниже
0.1. Метрики при этом считаются **без** весов — оцениваем на честной
популяции.

## 5. Метрики: что означает каждое число

### Brier score — главная метрика

Средний квадрат ошибки вероятности: `mean((p − y)²)`, где `y` это 0 или 1.
**Меньше — лучше.** Ноль — идеальное предсказание.

Ориентиры:

| значение | смысл |
|---|---|
| 0.25 | модель бесполезна — это Brier константы 0.5 |
| 0.18 | целевой порог проекта |
| 0.168 | текущий production на про-эталоне |
| 0.108 | текущий production на пабликах |

Важно: Brier **нельзя сравнивать между разными выборками**. На выборке,
где одна сторона побеждает в 90% случаев, легко получить низкий Brier,
ничего не понимая — достаточно всегда говорить 0.9.

### Skill score — Brier с поправкой на сложность выборки

```
uncertainty = p̄ · (1 − p̄)        где p̄ — доля побед Radiant в выборке
skill = 1 − Brier / uncertainty
```

Показывает, какую долю неопределённости модель реально объяснила. Ноль —
модель не лучше константы, единица — идеал. Именно эта величина позволяет
честно сравнивать паблики и про.

Текущее состояние: **0.58** на пабликах, **0.33** на про.

### Разновидности Brier в выводе обучения

```json
{"brier_oof": 0.1369, "brier_raw": 0.1262, "brier_calibrated": 0.1269,
 "brier_early": 0.1946, "brier_mid": 0.1005, "brier_late": 0.098,
 "brier_benchmark_pro": 0.1682, "benchmark_rows": 11317}
```

| поле | что это |
|---|---|
| `brier_raw` | до калибровки — техническая цифра, смотреть не надо |
| `brier_calibrated` | на валидационном сплите, после калибровки |
| `brier_oof` | на out-of-fold предсказаниях кросс-валидации — честная внутренняя оценка |
| `brier_benchmark_pro` | **главное число**: на про-эталоне, который модель не видела |
| `benchmark_rows` | размер эталона в строках. Сейчас должно быть около 11 тысяч |
| `brier_early` | 0–10 минут |
| `brier_mid` | 10–25 минут |
| `brier_late` | 25+ минут |

**Фазовые Brier важнее агрегата.** Поздняя игра тривиальна — когда база
снесена, предсказать исход легко, и `brier_late` всегда хороший. Ценность
модели в ранней игре, поэтому `brier_early` (сейчас 0.195) — самая
честная характеристика. Агрегат маскирует эту разницу.

### Смещение (bias)

Средний прогноз минус фактическая доля побед. Показывает систематический
перекос: модель в среднем завышает или занижает шансы Radiant.

Норма — около нуля. Текущее состояние: **+0.008** на про, **−0.012** на
пабликах. До правки калибровки на про было +0.035.

### PSI — дрейф распределения фич

Показывает, насколько данные, на которых работает модель сейчас,
отличаются от тех, на которых она обучалась.

| PSI | трактовка |
|---|---|
| < 0.1 | дрейфа нет |
| 0.1–0.25 | умеренный, стоит присмотреться |
| > 0.25 | сильный — переобучать |

Текущее значение 0.089, худшая фича `networth_rel`. Auto-train сам
инициирует переобучение при превышении порога.

## 6. Эталон, валидация и гейт

Три разные выборки, которые легко перепутать:

- **train** — на чём модель учится;
- **валидация (valid)** — часть непро-матчей, отложенная по группам;
- **про-эталон (benchmark)** — про-матчи, отведённые в holdout.

С 2026-07-31 про-матчи делятся между обучением и эталоном переменной
`PRO_TRAIN_FRAC` (по умолчанию 0.5). До этого весь про-tier был
holdout'ом, модель не видела этот домен вовсе и получала на нём skill
0.27 против 0.58 на пабликах.

**Гейт** решает, продвигать ли кандидата в production. Он не сравнивает
сохранённые метрики разных версий — это было бы нечестно, они считались
на разных данных. Вместо этого гейт прогоняет **обе** модели (кандидата и
текущий production) по одному и тому же holdout и сравнивает результат с
поправкой на шум:

```
registry: 0.8.0-20260731T071333Z promoted
(про-эталон, одни данные (278 матчей): new 0.1682 vs prod 0.1735
 (Δ-0.0053, σ0.0025) — не хуже prod)
```

Читать так: кандидат дал 0.1682, production на тех же данных 0.1735,
разница −0.0053 при шуме σ 0.0025. Продвигаем, если кандидат **не
значимо хуже** — то есть `Δ ≤ σ`. При равенстве в пределах шума
предпочтение новой версии: она обучена на большем объёме и устойчивее.

σ считается парным бутстрапом по матчам (200 итераций). Если Δ меньше σ,
разница неотличима от случайной.

## 7. Как проверить, что модель работает

### Проверка 0: данные, на которых модель стоит

```bash
make collect-report
```

Одна команда, весь дамп по входу модели: сколько матчей пришло за сутки
и **от какого источника**, что с квотами и токенами, какие фичи реально
заполнены (доля матчей с не-NaN по каждой колонке витрины — и отдельно
за последние 24 часа). Проверки 1–5 ниже смотрят на модель; эта смотрит
на то, из чего её обучают, и запускать её стоит первой: модель не может
быть лучше данных, а деградация данных начинается тихо — одна фича
перестаёт заполняться, а Brier проседает лишь через несколько
переобучений.

Ключевая строка — колонка «за 24ч» в таблице покрытия. Ненулевое общее
число матчей при нуле за сутки означает, что поставщик этой фичи
сломался сегодня.

### Проверка 1: статус

```bash
cd ~/manta && make ml-status
```

Смотреть: production-версия существует, `Brier эталон` ниже 0.18.

### Проверка 2: датасет не смещён

```bash
make ml-audit
```

Смотреть: дубликатов между tier — 0; длительности разумные (основная
масса 15–45 минут). Сдвиг приора train↔эталон — индикатор смещённости
выборки, но в обучение он не протекает (строки зеркалируются).

### Проверка 3: предсказания осмысленны

Взять три типичных матча (30–45 минут — не выбросы):

```bash
docker exec manta-clickhouse-1 clickhouse-client -q "
SELECT match_id, count() AS minutes, any(radiant_win) AS won
FROM manta.MatchTimelineFeatures FINAL
GROUP BY match_id HAVING minutes BETWEEN 30 AND 45
ORDER BY rand() LIMIT 3"
```

Прогнать каждый:

```bash
cd ~/manta/apps/ml-service && PYTHONPATH=src:$HOME/manta/libs \
  python3 -m explain.win_probability <MATCH_ID>
```

**Признаки исправной модели:**

- на первой минуте примерно 0.5 — модель ещё почти ничего не знает;
- к концу матча уверенно уходит к 0 или 1;
- финальная сторона совпадает с фактическим `won`;
- вклады фич осмысленны: в начале доминируют `networth_rel` и `xp_diff`,
  ближе к концу подключаются `towers_diff` и `rax_diff`.

Пример здорового выхода:

```
    60s  0.523 ###############        networth_diff+0.16  networth_rel-0.14
  2160s  1.000 ###################### xp_diff+1.60  towers_diff+0.96
```

### Проверка 4: калибровка и смещение

Скрипт целиком — в разделе 9. Смотреть колонку **смещение**: на обеих
выборках должно быть в пределах ±0.02.

### Проверка 5: сервис отвечает

```bash
curl -s localhost:9104/metrics | grep -E "ml_predictions_total|predict_latency"
```

Латентность порядка 1–3 мс на кадр. Нулевой счётчик не означает поломку —
просто к сервису не обращались.

## 8. Признаки, что модель сломана

| симптом | что это значит | куда смотреть |
|---|---|---|
| WP держится около 0.5 весь матч | модель ничего не выучила или фичи не доезжают | `make ml-audit`, проверить NaN в витрине |
| финальная WP указывает на проигравшего | серьёзная поломка — **но проверьте длительность матча** | раздел 9, ловушка №1 |
| WP на первой минуте сильно смещена (0.65+) | приор протекает через калибровку | проверка 4, смещение |
| `brier_benchmark_pro` > 0.18 | кандидат хуже цели; гейт его не пропустит | норма, ждать данных |
| все кандидаты подряд отклоняются | рост датасета не улучшает качество | смотреть `ml-audit`, возможно смещение выборки |
| `benchmark_rows` внезапно удвоился | `PRO_TRAIN_FRAC` не применился | проверить env и версию кода |
| PSI > 0.25 | мета изменилась (патч?) | переобучить |
| `brier_early` резко вырос | ранняя игра перестала предсказываться | проверить, не пропали ли фичи трека F |
| витрина не растёт | это не про модель, это сбор | `docs/runbooks.md`, runbook 1 |

## 9. Ловушки, на которых уже обжигались

**Ловушка 1: проверка на аномальном матче.** Матч длиной 111 минут —
экстремальный выброс; таких в обучении единицы. Модель там работает
вслепую, и её ошибка ничего не говорит о качестве. Всегда проверяйте на
матчах 30–45 минут.

**Ловушка 2: сравнение Brier между выборками.** 0.108 на пабликах и 0.168
на про — это **не** «модель деградировала на про». Это разные популяции.
Сравнивать можно только skill score или Brier на одной выборке.

**Ловушка 3: рост brier_oof после изменения выборки.** Когда в валидацию
добавили про-матчи, `brier_oof` вырос с 0.106 до 0.137. Это не
деградация: валидация стала труднее и честнее. Раньше она состояла из
одних пабликов и льстила.

**Ловушка 4: «аудит советует зеркальную аугментацию».** Она уже включена
с самого начала (`algo: lightgbm+oof-isotonic+mirror`). Сдвиг приора в
выводе `ml-audit` — характеристика сырого датасета, а не дефект обучения.

**Ловушка 5: калибровка не была симметричной.** Бустинг делали
симметричным зеркалированием, а калибратор учили на исходных парах — и он
возвращал приор обратно. Исправлено, но если увидите смещение на одной
стороне больше 0.03, проверьте, что в `algo` есть суффикс `+symcal`.

**Ловушка 6: маленький эталон шумит.** Эталон сейчас 278 матчей, σ гейта
около 0.0025. Уменьшать `PRO_TRAIN_FRAC`-остаток дальше нельзя — гейт
перестанет отличать реальные улучшения от случайных.

Скрипт проверки калибровки:

```bash
cd ~/manta/apps/ml-service && PYTHONPATH=src:$HOME/manta/libs python3 - <<'PY'
import json, os, numpy as np, requests
from predictors.win_probability import DEFAULT_MODEL, WinProbability
from training.dataset import match_rows_sql, row_to_features
m = WinProbability(str(DEFAULT_MODEL))
sql = match_rows_sql(extra=("radiant_win", "tier")) + " ORDER BY match_id, game_time"
r = requests.post(os.getenv("CLICKHOUSE_URL", "http://localhost:8123"),
    params={"database": "manta", "default_format": "JSONEachRow"}, data=sql,
    headers={"X-ClickHouse-User": "dota", "X-ClickHouse-Key": "dota_dev_password"},
    timeout=120)
r.raise_for_status()
rows = [json.loads(l) for l in r.text.splitlines() if l]
X = np.array([row_to_features(x) for x in rows])[:, :len(m.features)]
p, y = m.predict(X), np.array([int(x["radiant_win"]) for x in rows], float)
t = np.array([x.get("tier", "") for x in rows])
print(f"{'выборка':<16}{'ср.прогноз':>12}{'факт WR':>10}{'смещение':>11}{'Brier':>9}{'skill':>8}")
for name in ("Premium", "Professional"):
    s = t == name
    if s.any():
        br = ((p[s]-y[s])**2).mean(); unc = y[s].mean()*(1-y[s].mean())
        print(f"{name:<16}{p[s].mean():>12.3f}{y[s].mean():>10.3f}"
              f"{p[s].mean()-y[s].mean():>+11.3f}{br:>9.4f}{1-br/unc:>8.3f}")
PY
```

Учтите: этот замер оптимистичен, потому что часть про-матчей участвовала
в обучении. Он показывает **калибровку**, а не способность обобщать. За
обобщение отвечает гейт.

## 11. Переменные окружения

Все живут в `~/manta-train.env`.

| переменная | по умолчанию | что делает |
|---|---|---|
| `PRO_TRAIN_FRAC` | 0.5 | доля про-матчей в обучение. `0` — весь про в эталон (прежнее поведение) |
| `PATCH_OLD_WEIGHT` | 0.4 | множитель веса за каждый патч старости |
| `PATCH_LAG` | 1 | сколько патчей назад принимать при сборе. Поднять до 2, если приток встал после выхода патча |
| `REGISTRY_KEEP_LAST` | 10 | сколько версий хранить в реестре |

## 12. Что дальше

Главное ограничение сейчас — **объём датасета**. 1230 матчей для 22 фич
мало: модель упирается не в архитектуру, а в данные. Ревизия трека F
запланирована на 2–3 тысячи матчей.

гиперпараметры, а держать сбор живым. Проверять `make doctor` и следить,
что витрина растёт.

Смежные документы: `docs/runbooks.md` (что делать при инцидентах),
`docs/ML-PLAN.md` (план усиления модели), `docs/HANDOFF.md` (история
решений и почему сделано именно так).
